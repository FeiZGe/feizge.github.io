Security Governance & Frameworks

หัวข้อที่ 1

1. กรอบมาตรฐาน NIST Cybersecurity Framework (NIST CSF 2.0)

ออกสอบทุกรายละเอียด

NIST CSF 2.0 คือกรอบมาตรฐานสากลที่พัฒนาโดยสถาบันมาตรฐานและเทคโนโลยีแห่งชาติของสหรัฐอเมริกา เพื่อช่วยให้องค์กรทุกขนาดสามารถบริหารจัดการและลดความเสี่ยงทางไซเบอร์ได้อย่างเป็นระบบ จุดเปลี่ยนสำคัญที่สุดจากเวอร์ชัน 1.1 มาเป็น 2.0 คือการขยายขอบเขตจากเดิมที่เน้นเฉพาะโครงสร้างพื้นฐานสำคัญ (Critical Infrastructure) ให้ครอบคลุมองค์กรทุกประเภท และเพิ่มฟังก์ชันที่ 6 คือ Govern (GV) ไว้ตรงกลางวงกลม เพื่อเป็นแกนหลักในการควบคุมอีก 5 ฟังก์ชันที่เหลือ

Feynman Technique: อธิบาย NIST CSF 2.0 ให้เข้าใจเหมือนระบบรักษาความปลอดภัย "หมู่บ้านจัดสรร"

ลองจินตนาการว่าเรากำลังดูแลหมู่บ้านจัดสรรขนาดใหญ่:
• Govern (GV - นิติบุคคลและกฎหมู่บ้าน): คณะกรรมการหมู่บ้านที่ตั้งกฎระเบียบ จัดสรรงบจ้างยาม กำหนดว่าใครรับผิดชอบอะไร และตรวจบริษัทรับเหมาภายนอก (Supply Chain) ไม่ให้เอาโจรแฝงตัวเข้ามา
• Identify (ID - สำรวจทรัพย์สิน): เดินจดบันทึกว่าในหมู่บ้านมีบ้านกี่หลัง ประตูทางเข้ากี่บาน กล้องวงจรปิดอยู่ไหนบ้าง และจุดไหนเปลี่ยวหรือเสี่ยงโจรปีนเข้ามากที่สุด
• Protect (PT - สร้างรั้วและติดกุญแจ): ติดตั้งไม้กั้นแลกบัตร (IAM/MFA), สร้างกำแพงสูง, ติดลูกกรงเหล็กดัด (Encryption) และอบรมลูกบ้านไม่ให้เปิดประตูรับคนแปลกหน้า
• Detect (DE - กล้องวงจรปิดและสัญญาณกันขโมย): เปิดกล้อง CCTV และเซ็นเซอร์ตรวจจับความเคลื่อนไหวตลอด 24 ชั่วโมง ทันทีที่มีคนปีนรั้ว สัญญาณเตือนภัยต้องดังทันที (CloudTrail / GuardDuty)
• Respond (RS - หน่วยรปภ. เข้าระงับเหตุ): เมื่อสัญญาณดัง ยามวิ่งไปล็อกโซนนั้นทันที (Containment) ไม่ให้โจรหนีไปบ้านอื่น แจ้งตำรวจ และไล่โจรออกจากพื้นที่
• Recover (RC - ซ่อมแซมและถอดบทเรียน): ซ่อมประตูที่พังให้ลูกบ้านกลับมาใช้ชีวิตได้ตามปกติ (Restore Backup) แล้วประชุมสรุปบทเรียน (Lessons Learned) ว่าทำไมโจรถึงปีนเข้ามาได้ เพื่อเสริมรั้วให้สูงขึ้น

รายละเอียดเจาะลึกทั้ง 6 ฟังก์ชันหลัก (6 Core Functions)

1. GOVERN (GV) - การกำกับดูแล ฟังก์ชันใหม่ใน 2.0

กำหนดบริบทองค์กร กลยุทธ์การบริหารความเสี่ยง บทบาทหน้าที่ความรับผิดชอบ นโยบายความปลอดภัย และการบริหารความเสี่ยงของซัพพลายเชน (Cybersecurity Supply Chain Risk Management - C-SCRM)

สถานการณ์ตัวอย่าง: บอร์ดบริหารออกนโยบายบังคับว่าผู้ให้บริการ Cloud และ Vendor ทุกรายที่เชื่อมต่อกับบริษัทต้องผ่านมาตรฐาน ISO 27001 และมีการทำสัญญา NDA
2. IDENTIFY (ID) - การระบุและสำรวจ Asset & Risk

ทำความเข้าใจความเสี่ยงปัจจุบันด้วยการทำบัญชีสินทรัพย์ (Asset Management) ทั้ง Hardware, Software, ข้อมูล, ระบบคลาวด์ และประเมินช่องโหว่ (Risk Assessment) เพื่อจัดลำดับความสำคัญ

สถานการณ์ตัวอย่าง: ใช้ AWS Config และ Systems Manager Inventory สำรวจว่าในบัญชี AWS ของบริษัทมี EC2 กี่เครื่อง มี S3 กี่ถัง และถังไหนเก็บข้อมูลลูกค้าบ้าง
3. PROTECT (PT) - การป้องกัน Preventive Control

สร้างเกราะป้องกันเพื่อลดโอกาสเกิดเหตุโจมตี เช่น การควบคุมสิทธิ์ (IAM & MFA), การเข้ารหัสข้อมูล (Data Security), ความปลอดภัยแพลตฟอร์ม และการอบรมพนักงาน (Awareness Training)

สถานการณ์ตัวอย่าง: บังคับให้พนักงานทุกคนต้องเปิด MFA ก่อน Login เข้า AWS, เข้ารหัสฐานข้อมูล RDS ด้วย KMS และตั้งค่า Security Group เปิดเฉพาะพอร์ต 443
4. DETECT (DE) - การตรวจจับ Detective Control

การเฝ้าระวังอย่างต่อเนื่อง (Continuous Monitoring) และการวิเคราะห์เหตุการณ์ผิดปกติ (Adverse Event Analysis) เพื่อตรวจพบการบุกรุกหรือความผิดปกติให้เร็วที่สุด

สถานการณ์ตัวอย่าง: เปิดใช้งาน Amazon GuardDuty และ CloudTrail จับได้ว่ามีคนพยายาม Login ด้วย Root Account จากต่างประเทศตอนตี 3 แล้วส่งแจ้งเตือนทันที
5. RESPOND (RS) - การตอบสนอง Incident Containment

การลงมือปฏิบัติการเมื่อตรวจพบภัยคุกคาม ตั้งแต่การกักกันความเสียหาย (Incident Containment), การวิเคราะห์หาสาเหตุ, การกำจัดต้นตอ (Eradication) และการรายงานสื่อสาร

สถานการณ์ตัวอย่าง: เมื่อพบว่า EC2 ติดมัลแวร์ขุดเหรียญ ระบบ EventBridge สั่งรัน Lambda เปลี่ยน Security Group ของเครื่องนั้นเป็น Quarantine SG ทันทีเพื่อตัดเน็ต
6. RECOVER (RC) - การฟื้นฟูและกู้คืน Resilience & Restore

การกู้คืนระบบและข้อมูลที่ได้รับผลกระทบให้กลับมาทำงานได้ตามปกติ (Incident Recovery Plan Execution) พร้อมการสื่อสารสถานะและสรุปบทเรียน (Lessons Learned)

สถานการณ์ตัวอย่าง: กู้คืนฐานข้อมูลจาก RDS Snapshot ที่ปลอดภัยก่อนโดนแฮก เปิดเซิร์ฟเวอร์ชุดใหม่จาก Golden AMI และปรับปรุงแผนรับมือ

CSF Organizational Profiles & 3 ระดับการสื่อสาร

Organizational Profile คือการประเมินสถานะความปลอดภัยขององค์กรเทียบกับผลลัพธ์ของ CSF Core แบ่งออกเป็น:

  • Current Profile (สถานะปัจจุบัน): ระบุว่าปัจจุบันองค์กรทำอะไรอยู่และบรรลุผลระดับใด
  • Target Profile (สถานะเป้าหมาย): ระบุเป้าหมายด้านความปลอดภัยที่องค์กรต้องการไปให้ถึง เพื่อนำมาวิเคราะห์ช่องว่าง (Gap Analysis) และจัดลำดับความสำคัญ
การสื่อสารความเสี่ยง 3 ระดับในองค์กร:
1. Executive Level (ผู้บริหาร): เน้นความเสี่ยงระดับองค์กร ตัดสินใจลำดับความสำคัญของภารกิจและงบประมาณ (Risk Appetite)
2. Business/Process Level (ผู้จัดการ): บริหารความเสี่ยงโครงสร้างพื้นฐาน เลือก Framework Profile และจัดสรรงบ
3. Implementation/Operational Level (ผู้ปฏิบัติงาน): นำ Profile ไปลงมือตั้งค่าระบบจริง และรายงานความคืบหน้า/ช่องโหว่กลับขึ้นไป

CSF Tiers ทั้ง 4 ระดับ (ระดับความเข้มข้นในการบริหารความเสี่ยง)

ใน CSF 2.0 ปรับเกณฑ์เป็น: Cybersecurity Risk Governance, Cybersecurity Risk Management และ Third-Party Cybersecurity Risks

Tier 1: Partial (ทำเป็นครั้งคราว): จัดการความเสี่ยงแบบเฉพาะหน้า (Ad hoc) ไม่มีนโยบายเป็นทางการ ต่างคนต่างทำ ไม่รู้ความเสี่ยงของ Supplier
Tier 2: Risk Informed (ตระหนักรู้ความเสี่ยง): ผู้บริหารอนุมัติแนวทางแล้ว แต่ยังไม่ได้บังคับใช้เป็นนโยบายทั่วทั้งองค์กร แชร์ข้อมูลกันแบบไม่เป็นทางการ
Tier 3: Repeatable (ทำซ้ำได้อย่างเป็นระบบ): มีนโยบายทางการระดับองค์กร มีการทบทวนสม่ำเสมอ มีสัญญาและการจัดการความเสี่ยง Supplier อย่างเป็นระบบ
Tier 4: Adaptive (ปรับตัวอัตโนมัติเชิงรุก): ความปลอดภัยเป็นวัฒนธรรมองค์กร ใช้ข้อมูล Real-time และเทคโนโลยีขั้นสูง/AI คาดการณ์และปรับตัวรับภัยคุกคามใหม่อย่างต่อเนื่อง

2. AWS Well-Architected Framework: 6 เสาหลัก (6 Pillars)

Feynman Technique: เปรียบเทียบ 6 Pillars เหมือน "การสร้างตึกคอนโดมิเนียมหรู"

การสร้างระบบ Cloud ที่ดีไม่ใช่แค่โค้ดรันผ่าน แต่ต้องเหมือนสร้างตึกที่มี 6 เสาหลักค้ำยัน: 1. Security (มียามและระบบคีย์การ์ดแน่นหนา), 2. Reliability (มีเครื่องปั่นไฟสำรอง น้ำไฟไม่เคยดับ), 3. Operational Excellence (นิติบุคคลทำงานเป็นระเบียบ มีคู่มือชัดเจน), 4. Performance Efficiency (ลิฟต์ความเร็วสูงทันสมัย ไม่รอนาน), 5. Cost Optimization (ไม่เปิดแอร์ทิ้งในห้องว่าง ประหยัดงบ), และ 6. Sustainability (ตึกประหยัดพลังงาน เป็นมิตรต่อสิ่งแวดล้อม)

เสาหลัก (Pillar) จุดเน้นหลัก (Core Focus) กลไกสำคัญ (Key Mechanisms) เป้าหมายสูงสุด (Ultimate Goal)
1. Security (ความปลอดภัย) ปกป้องข้อมูล ระบบ และสินทรัพย์ IAM, Log Analysis, Encryption, Defense in Depth Protection & Incident Readiness
2. Reliability (ความเสถียร) ป้องกันความล้มเหลวและฟื้นตัวไว High Availability, Auto-recovery, Horizontal Scaling Meet Business Demand & Resilience
3. Operational Excellence กระบวนการทำงานและปฏิบัติการ Operations as Code, CI/CD, Continuous Improvement Deliver Business Value Smoothly
4. Performance Efficiency การใช้ทรัพยากรไอทีอย่างคุ้มสมรรถนะ Right-sizing, Serverless, Global CDN Maximize Efficiency & Speed
5. Cost Optimization การบริหารจัดการต้นทุน Pay-as-you-go, Spot/Reserved Instances, Auto Scaling Avoid Unneeded Costs (Eliminate Waste)
6. Sustainability (ความยั่งยืน) ลดผลกระทบต่อสิ่งแวดล้อม Graviton Processors, Green Regions, High Utilization Reduce Carbon Footprint

3. เจาะลึก Security Pillar: 7 หลักการออกแบบ & 5 ขอบเขตหลัก

7 Design Principles for Security (7 หลักการออกแบบความปลอดภัยบนคลาวด์)

1. Implement a strong identity foundation

บังคับใช้สิทธิ์เท่าที่จำเป็น (Least Privilege), เลิกใช้รหัสผ่านถาวร (ใช้ IAM Role แทน), ห้ามใช้ Root Account ทำงานประจำวัน และเปิด MFA เสมอ

2. Enable traceability (Audit Trail)

เปิดบันทึก Log ทุกการกระทำและ API Calls แบบ Real-time (CloudTrail, CloudWatch, VPC Flow Logs) เพื่อสืบย้อนได้ว่าใครทำอะไรเมื่อไหร่

3. Apply security at all layers (Defense in Depth)

วางเกราะป้องกันหลายชั้นซ้อนกัน ตั้งแต่ Edge (WAF/Shield) -> VPC -> Subnet (NACL) -> Instance (Security Group) -> OS -> Application -> Data

4. Automate security best practices

ใช้ซอฟต์แวร์อัตโนมัติตรวจจับและแก้ปัญหา (Auto-Remediation) เช่น ถ้ามีคนเผลอเปิด S3 Public ให้ Lambda วิ่งไปปิดล็อกกลับภายใน 3 วินาที

5. Protect data in transit and at rest

จำแนกชั้นความลับข้อมูล และเข้ารหัสข้อมูลทั้งขณะเดินทางผ่านเน็ต (TLS/HTTPS) และขณะเก็บนิ่งในดิสก์ (KMS AES-256)

6. Keep people away from data

ลดการให้มนุษย์เข้าไปจับข้อมูลดิบหรือ SSH เข้าเซิร์ฟเวอร์โดยตรง (ลด Human Error และขโมยข้อมูล) ให้ทำงานผ่าน CI/CD Pipeline หรือ自动化 Tool แทน

7. Prepare for security events

เตรียมแผนรับมือเหตุฉุกเฉิน และจัดซ้อมรบจำลองสถานการณ์โดนแฮก (GameDays) สม่ำเสมอ เพื่อให้ทีมรู้ขั้นตอนการทำงานเมื่อเกิดวิกฤตจริง

5 Security Domains (5 ขอบเขตเครื่องมือความปลอดภัยบน AWS)

Domain หน้าที่หลัก บริการ AWS ที่ต้องจำไปสอบ
1. Identity & Access Management ยืนยันตัวตน (Authentication) และตรวจสอบสิทธิ์ (Authorization) AWS IAM, MFA Token, IAM Identity Center (SSO), AWS Organizations (SCPs)
2. Detective Controls ตรวจจับความผิดปกติผ่านการเก็บและวิเคราะห์ Log AWS CloudTrail, AWS Config, Amazon CloudWatch, Amazon GuardDuty, Security Hub
3. Infrastructure Protection ปกป้องเครือข่ายและเครื่องเซิร์ฟเวอร์ Amazon VPC, Security Groups, NACLs, AWS WAF, AWS Shield
4. Data Protection เข้ารหัส สำรองข้อมูล และป้องกันข้อมูลรั่วไหล AWS KMS, Amazon S3, Amazon EBS, Amazon RDS, ELB (TLS), Amazon Macie
5. Incident Response ตอบสนอง กักกัน และกู้คืนระบบอัตโนมัติ AWS IAM, AWS CloudFormation, AWS Lambda, Amazon EventBridge

1. 5 หลักการออกแบบความเสถียร (5 Design Principles for Reliability)

1. Automatically recover from failure (ฟื้นตัวอัตโนมัติ)

ติดตั้งระบบตรวจวัดสุขภาพ (Health Checks) และทำ Self-healing Architecture เช่นเมื่อ EC2 ค้าง ระบบ Auto Scaling จะสั่ง Terminate เครื่องที่พังและเปิดเครื่องใหม่ขึ้นมาแทนทันทีโดยไม่ต้องรอแอดมินตื่นมาแก้

2. Test recovery procedures (ทดสอบการกู้คืนเสมอ)

บน Cloud เราสามารถจำลองเหตุการณ์พังจริงได้ (Chaos Engineering / AWS Fault Injection Simulator) เพื่อพิสูจน์ว่าไฟล์ Backup กู้ได้จริงและระบบสลับสาย (Failover) ทำงานได้ไม่ติดขัด

3. Scale horizontally to increase aggregate availability

ขยายแนวนอน (Horizontal Scaling / Scale Out) คือการเพิ่มจำนวนเครื่องเล็กๆ หลายเครื่องช่วยกันรับงาน แทนการอัปเกรดเครื่องเดียวให้ใหญ่ขึ้น (Vertical Scaling) เพื่อกำจัด Single Point of Failure (SPOF)

4. Stop guessing capacity (เลิกเดาขนาดเซิร์ฟเวอร์)

ถ้าเดาเผื่อมากเกินไปก็เปลืองเงิน (Idle resource) ถ้าเดาน้อยไปเว็บก็ล่มตอนคนเข้าเยอะ ให้ใช้ Auto Scaling เพิ่ม-ลดจำนวนเซิร์ฟเวอร์ตามปริมาณคนเข้าใช้งานจริงอัตโนมัติ

5. Manage change in automation (จัดการการเปลี่ยนแปลงด้วยระบบอัตโนมัติ)

การแก้ค่าระบบด้วยมือ (Manual Change) มักทำให้เกิดการตั้งค่าผิดพลาด ควรใช้ Infrastructure as Code (Terraform / CloudFormation) เพื่อให้อัปเดตและ Rollback ได้อย่างแม่นยำ

Feynman Technique: Horizontal Scaling (Scale Out) vs Vertical Scaling (Scale Up)

สมมติร้านกาแฟมีลูกค้าทะลักเข้ามา 100 คน:
• Vertical Scaling (Scale Up): จ้างบาริสต้าเทพ 1 คนที่ชงเร็วขึ้น 5 เท่า แต่ถ้าวันไหนบาริสต้าคนนี้ป่วยเข้าโรงพยาบาล ร้านต้องปิดทันที! (เกิด Single Point of Failure)
• Horizontal Scaling (Scale Out): จ้างบาริสต้าฝีมือมาตรฐาน 5 คนมายืนเรียงกัน ถ้าคนหนึ่งปวดท้องไปเข้าห้องน้ำ อีก 4 คนที่เหลือก็ยังชงกาแฟให้ลูกค้าได้ต่อเนื่อง ร้านไม่เคยหยุดให้บริการ!

RPO (Recovery Point Objective)

"ข้อมูลหายย้อนหลังได้ไม่เกินกี่นาที/ชั่วโมง?" เป็นตัวชี้วัดที่กำหนด ความถี่ในการทำ Backup เช่น ถ้าธุรกิจบอกว่า RPO = 1 ชั่วโมง แปลว่าถ้าเว็บพังตอนบ่ายโมง ข้อมูลต้องย้อนกลับไปได้ไม่เกินเที่ยงตรง (ต้องตั้ง Backup อัตโนมัติทุกๆ 1 ชั่วโมง)

RTO (Recovery Time Objective)

"ระบบล่มนานสุดได้ไม่เกินกี่นาที/ชั่วโมง?" เป็นตัวชี้วัดที่กำหนด ความเร็วในการกู้คืนระบบ (Downtime สูงสุดที่ยอมรับได้) เช่น ถ้า RTO = 15 นาที แปลว่าตั้งแต่เกิดเรื่องตอน 13:00 น. ระบบสำรองต้องรับงานต่อให้เสร็จก่อน 13:15 น.

3. กลยุทธ์ Disaster Recovery บนคลาวด์ 4 รูปแบบ (4 DR Strategies)

Feynman Technique: เปรียบเทียบ 4 DR Strategies เหมือน "การเตรียมบ้านสำรองเผื่อน้ำท่วมบ้านหลัก"

• 1. Backup & Restore (เช่าโกดังเก็บของ): เราแค่แพ็กเสื้อผ้าและพิมพ์เขียวบ้านไปฝากไว้ในโกดังต่างจังหวัด ถ้าน้ำท่วมบ้านหลัก เราต้องไปหาเช่าที่ดิน กางเต็นท์ และประกอบเฟอร์นิเจอร์ใหม่ทั้งหมด (ถูกที่สุด แต่ใช้เวลาย้ายเข้าอยู่นานเป็นวัน)
• 2. Pilot Light (บ้านสำรองที่เปิดเฉพาะตู้เย็นทิ้งไว้): คำว่า Pilot Light มาจาก "ไฟล่อหัวแก๊ส" เราสร้างบ้านสำรองไว้แล้วและเสียบปลั๊กตู้เย็น (Database) ให้มีอาหารสดซิงค์ตรงจากบ้านหลักตลอดเวลา แต่ปิดไฟปิดแอร์ทุกห้อง (ปิด Web/App Server) พอเกิดเหตุแค่สับคัตเอาต์เปิดแอร์ก็เข้าอยู่ได้เลย (เร็วขึ้นระดับสิบนาที ประหยัดค่าไฟ)
• 3. Warm Standby (บ้านสำรองขนาดกะทัดรัดที่เปิดแอร์รอไว้แล้ว): บ้านสำรองเปิดน้ำเปิดไฟเปิดแอร์ครบทุกห้องพร้อมอยู่ทันที แต่เปิดแอร์ตัวเล็กไว้ก่อน พอคนย้ายมาจริงค่อยเร่งแอร์และกางเตียงเสริม (Scale Out) (ย้ายเข้าได้ในไม่กี่นาที)
• 4. Multi-Site Active-Active (มีบ้านหรู 2 หลังที่อาศัยอยู่พร้อมกัน): ครอบครัวแบ่งกันอยู่ทั้งบ้านกรุงเทพฯ และบ้านเชียงใหม่ตลอดเวลา ถ้าน้ำท่วมกรุงเทพฯ ทุกคนแค่บินไปรวมตัวที่เชียงใหม่ได้ทันทีโดยชีวิตไม่สะดุดเลยแม้แต่วินาทีเดียว (RTO/RPO แทบเป็น 0 แต่แพงที่สุด)

กลยุทธ์ DR สิ่งที่รันอยู่ใน DR Region ยามปกติ สิ่งที่ต้องทำเมื่อเกิดภัยพิบัติ RTO / RPO ต้นทุน (Cost)
1. Backup & Restore ไม่มี Server รันอยู่เลย มีเฉพาะไฟล์ Snapshot/Backup บน S3 รัน IaC สร้างระบบใหม่ทั้งหมด + Restore ข้อมูลจาก Backup ชั่วโมง - วัน $ (ต่ำสุด)
2. Pilot Light รันเฉพาะ Core Database เพื่อ Sync ข้อมูล ส่วน App/Web Server ปิดไว้ สั่งสตาร์ท EC2/App Server จาก AMI ที่เตรียมไว้และสลับ DNS 10 - 60 นาที $$ (ปานกลาง)
3. Warm Standby รันครบทุก Tier (Web + App + DB) แต่ใช้สเปกเล็กหรือจำนวนน้อย สลับ Route 53 มาที่ DR และสั่ง Auto Scaling ขยายขนาดเต็มกำลัง ไม่กี่นาที $$$ (สูง)
4. Multi-Site Active-Active รันเต็มรูปแบบ (Full Production Capacity) รับทราฟฟิกจริงทั้ง 2 Regions Route 53 ตัดทราฟฟิกจากฝั่งที่ล่มไปยังฝั่งที่ปกติอัตโนมัติ วินาที / Near-Zero $$$$ (สูงสุด)

Cloud Data Protection, States of Data & AWS KMS

บทเรียนสำคัญที่สุดสำหรับการสอบ: การจำแนกข้อมูล 5 ระดับ (Level 0-4), 3 States of Data พร้อมตัวอย่างที่ต้องจำให้ขึ้นใจ, รายการ Securing the 3 States of Data (แบบตรงเป๊ะสำหรับสอบเติมคำ), วงจรชีวิตข้อมูล 6 ขั้นตอน, AWS Storage Gateway และ Envelope Encryption บน AWS KMS

1. การจำแนกประเภทข้อมูล (Data Classification: 5 ระดับในสไลด์เรียน)

Feynman Technique: ทำไมเราต้องแยกประเภทข้อมูล (Data Classification)?

ถ้าเราเอา "ใบปลิวโฆษณาร้านอาหาร" ไปเก็บในตู้เซฟธนาคารที่ต้องสแกนม่านตา 3 ชั้น มันก็เปลืองเงินและเสียเวลาทำงานใช่ไหมครับ? ในทางกลับกัน ถ้าเราเอา "รหัสบัตรเครดิตลูกค้า" ไปแปะไว้ที่บอร์ดหน้าบริษัท บริษัทก็เจ๊งทันที! ดังนั้น Data Classification จึงเป็นการแปะป้ายบอกระดับความลับของข้อมูล เพื่อจะได้เลือกล็อกกุญแจ (Security Control) ให้เหมาะสมกับมูลค่าและความเสี่ยงของข้อมูลแต่ละชนิด

ขั้นที่ 1: กำหนดระดับอ่อนไหว

กำหนดมาตรฐานชี้วัดและนิยามระดับความอ่อนไหว (Sensitivity Level) โดยพิจารณาจากความเป็นข้อมูลส่วนบุคคล (PDPA/GDPR) และความเสี่ยงในการรั่วไหล

ขั้นที่ 2: กำหนดเกณฑ์การประเมิน

ออกแบบแบบประเมิน (Template) ระบุหน้าที่ผู้ประเมิน และประเมินข้อมูลอย่างมีหลักการในรูปแบบคะแนนเมตริก (Metric Score)

ขั้นที่ 3: ร่างนโยบายต้นแบบ

ติดป้ายจำแนกข้อมูล (Classification Label) เพื่อนำไปกำหนดสิทธิ์การเข้าถึงและการเข้ารหัสตามหลัก Data Security

ระดับความอ่อนไหว (Sensitivity Level) การจำแนกข้อมูล (Label) การเข้าถึง (Accessibility) ตัวอย่างข้อมูล (ตามสไลด์เรียน) การควบคุมความปลอดภัย
Level 0 - None เปิดเผยได้ (Public Used) ทุกคนสามารถเข้าถึงได้ ข้อมูล PR, ข้อมูล Website, ข้อมูลบริษัท, Press releases เน้น Integrity & Availability (ไม่ต้องเข้ารหัสลับ)
Level 1 - Low ใช้ภายใน (Internal Used Only) พนักงานทั่วไปภายในองค์กร ข้อมูลบริการ, ข้อมูลการตลาด, ข้อมูลจัดซื้อ จำกัดเฉพาะพนักงาน (Internal Login)
Level 2 - Medium ลับ (Confidential) ผู้บริหาร / IT / คณะทำงานธรรมาภิบาลข้อมูล (ต้องขอสิทธิ์) ข้อมูลการเงิน, ข้อมูลรายได้การขาย, ข้อมูล NDA / สัญญา IAM (Need-to-know), Encryption at Rest, Logging
Level 3 - High ลับมาก (Highly Confidential) ผู้บริหารระดับสูง / IT เฉพาะกิจ (ต้องขออนุมัติสิทธิ์) ข้อมูลลูกค้า, ข้อมูลภายใน IT System, ข้อมูลพนักงานรายบุคคล Strict IAM + MFA, KMS Encryption, Real-time Audit
Level 4 - Extreme ลับที่สุด (Restricted) เจ้าของข้อมูล (Data Owner) เท่านั้น (ต้องขอสิทธิ์พิเศษ) ข้อมูลส่วนบุคคล (PII), Credit Card, ข้อมูลส่วนบุคคลอ่อนไหว, รหัสผ่าน DB Secret Vault, Rotation, Continuous Audit, Strict Access Control

2. เจาะลึก 3 สภาวะของข้อมูล (States of Data)

ออกสอบแยกประเภทและตัวอย่าง
Feynman Technique: เปรียบเทียบ 3 States of Data เหมือน "เงินสดของธนาคาร"

• Data at Rest (เงินที่นอนนิ่งอยู่ในห้องนิรภัย): ข้อมูลที่ถูกเซฟเก็บไว้เฉยๆ ในฮาร์ดดิสก์ ในเทปแบ็กอัป หรือใน S3 วิธีป้องกันคือล็อกตู้เซฟให้แน่น (เข้ารหัสไฟล์ / Full Disk Encryption)
• Data in Motion / In Transit (เงินที่กำลังขนอยู่บนรถขนเงินวิ่งบนถนน): ข้อมูลที่กำลังวิ่งผ่านสายแลนหรืออินเทอร์เน็ต เช่น กำลังกดส่งอีเมล หรือดาวน์โหลดไฟล์ วิธีป้องกันคือใช้รถหุ้มเกราะกันกระสุน (สร้างอุโมงค์ HTTPS/TLS หรือ VPN)
• Data in Use (เงินที่พนักงานกำลังวางนับอยู่บนเคาน์เตอร์): ข้อมูลที่ถูกเปิดขึ้นมาอ่านหรือคำนวณอยู่ใน RAM หรือ CPU เช่น เปิดไฟล์ Word พิมพ์งานอยู่ ตอนนี้ข้อมูลต้องถูกถอดรหัสออกมาให้อ่านได้ จึงต้องคุมเข้มว่า "ใครมีสิทธิ์มายืนตรงเคาน์เตอร์นี้บ้าง" (RBAC, Identity Management, DRM และ Confidential Computing)

สภาวะที่ 1

Data at Rest

ข้อมูลที่ถูกจัดเก็บนิ่งๆ อยู่ในอุปกรณ์ เช่น ฮาร์ดดิสก์, คลาวด์ หรือฐานข้อมูล

ตัวอย่างจากภาพสไลด์ (ต้องจำเป๊ะ):
  • BACKUP FILES (ไฟล์สำรองข้อมูล)
  • ARCHIVED FILES (ไฟล์เก็บถาวร)
  • STORED FILES (ไฟล์ที่เก็บในดิสก์/S3)
มักป้องกันด้วย: การเข้ารหัสไฟล์/ดิสก์ (AES-256, KMS, EBS/S3 Encryption)

4. วงจรชีวิตของข้อมูล (Data Lifecycle Management - 6 ขั้นตอน)

Stage 1

1. Create (การสร้างข้อมูล)

การสร้างข้อมูลใหม่ การรับข้อมูลเข้าจากฟอร์มลูกค้า หรือการอัปเดตข้อมูลเดิม ต้องติดป้าย Classification ทันทีที่สร้าง

Stage 2

2. Store (การจัดเก็บข้อมูล)

การนำข้อมูลไปเก็บบน Cloud Storage หรือ Database พร้อมทำ Encryption at Rest, Access Control และ Backup

Stage 3

3. Use (การใช้งานข้อมูล)

การดึงข้อมูลมาเปิดดู ประมวลผล หรือแก้ไขในแอปพลิเคชัน ควบคุมด้วย RBAC, DLP และ DRM

Stage 4

4. Publish / Share (การเผยแพร่และแชร์)

การส่งมอบเอกสาร แลกเปลี่ยน หรือแชร์ข้อมูลให้ลูกค้าหรือพาร์ทเนอร์ภายนอก ต้องทำ Data Masking หรือเข้ารหัสระหว่างส่ง

Stage 5

5. Archive / Achieve (การจัดเก็บถาวร)

Stage 6

6. Destroy (การทำลายข้อมูล)

การลบทำลายข้อมูลอย่างถาวรเมื่อหมดอายุความจำเป็น (เช่น Crypto-shredding หรือการทำลายกุญแจ KMS) เพื่อไม่ให้กู้คืนกลับมาได้อีก

5. AWS Storage Gateway & AWS KMS (Envelope Encryption)

AWS Storage Gateway ทั้ง 3 รูปแบบ (เชื่อม On-Premises สู่ Cloud)

  • 1. File Gateway (Amazon S3 File Gateway): เก็บและเข้าถึงไฟล์ผ่านโปรโตคอล NFS หรือ SMB โดยแปลงเป็น Object เก็บใน Amazon S3 เบื้องหลัง
  • 2. Volume Gateway: ให้บริการ Block Storage ผ่านโปรโตคอล iSCSI สำรองเป็น EBS Snapshot (แบ่งเป็น Stored Volumes เก็บข้อมูลหลักที่บริษัท และ Cached Volumes เก็บข้อมูลหลักบน S3 แล้วแคชที่ใช้บ่อยไว้ที่บริษัท)
  • 3. Tape Gateway (VTL): จำลองระบบเทปสำรองข้อมูลเสมือน (Virtual Tape Library) ส่งข้อมูลไปเก็บถาวรใน S3 Glacier / Deep Archive

3 ประเภทกุญแจใน AWS KMS (Key Management Service)

  • 1. AWS Owned Keys: AWS สร้างและใช้เองเบื้องหลัง ลูกค้ามองไม่เห็น จัดการไม่ได้ ฟรี
  • 2. AWS Managed Keys (เช่น aws/s3, aws/rds): AWS สร้างให้ในบัญชีเรา หมุนเวียนกุญแจ (Rotation) อัตโนมัติทุก 1 ปี แก้ไข Policy เองไม่ได้
  • 3. Customer Managed Keys (CMK): ลูกค้าสร้างเอง กำหนด Key Policy เองได้ เปิด Auto Rotation ได้ สั่งลบหรือนำเข้ากุญแจเองได้ (มีค่าใช้จ่าย)
Feynman Technique: Envelope Encryption (การเข้ารหัสแบบซองจดหมาย) คืออะไร ทำไมไม่ใช้ Master Key ล็อกไฟล์ตรงๆ?

AWS KMS มีข้อจำกัดว่า รับข้อมูลไปเข้ารหัสตรงๆ ได้ไม่เกิน 4 KB ต่อครั้ง ถ้าเรามีไฟล์วิดีโอขนาด 50 GB เราส่งเข้า KMS ตรงๆ ไม่ได้!
วิธีแก้คือ Envelope Encryption:
1. แอปของเราขอให้ KMS สร้างลูกกุญแจดอกเล็กที่ชื่อว่า Data Encryption Key (DEK) ออกมา 2 ร่าง คือ ร่างกุญแจจริง (Plaintext DEK) และ ร่างกุญแจที่ถูกใส่ซองล็อกด้วยแม่กุญแจใหญ่ KEK แล้ว (Encrypted DEK)
2. แอปนำ กุญแจจริง (Plaintext DEK) มาล็อกไฟล์วิดีโอ 50 GB ในเครื่องตัวเองอย่างรวดเร็ว พอล็อกเสร็จ ทุบกุญแจจริงใน RAM ทิ้งทันที!
3. เอา ซองกุญแจที่ล็อกแล้ว (Encrypted DEK) แปะติดไว้คู่กับไฟล์วิดีโอที่เข้ารหัสแล้ว
4. วันหน้าถ้าจะเปิดดูวิดีโอ แอปไม่ต้องส่งไฟล์ 50 GB ไปหา KMS แค่ส่ง "ซองกุญแจเล็กๆ" ไปให้ KMS ใช้แม่กุญแจใหญ่ (KEK) แกะซองเอาลูกกุญแจจริงกลับมาไขไฟล์วิดีโอ!

3. เปรียบเทียบชัดๆ: AWS Secrets Manager vs. SSM Parameter Store

หัวข้อเปรียบเทียบ AWS Secrets Manager SSM Parameter Store
Automated Rotation (การหมุนเวียนรหัสอัตโนมัติ) รองรับการหมุนเวียนอัตโนมัติในตัว (Built-in Lambda integration สำหรับ RDS, Redshift, DocumentDB) ไม่รองรับในตัว (ต้องเขียนโค้ด Lambda + EventBridge ทำเอง)
Cost (ค่าใช้จ่าย) มีค่าใช้จ่าย ($0.40 / Secret / เดือน + $0.05 ต่อ 10,000 API calls) มี Free Tier สำหรับ Standard Parameters (สูงสุด 10,000 พารามิเตอร์ ฟรี!)
Primary Use Case (การใช้งานหลัก) เหมาะสำหรับรหัสผ่านฐานข้อมูล, API Keys, OAuth Tokens และข้อมูลลับที่ต้องเปลี่ยนบ่อย เหมาะสำหรับเก็บค่า Configuration ทั่วไป เช่น ENV=prod, URL, AMI ID หรือรหัสลับที่ไม่ต้องหมุนเวียนบ่อย
Cross-Account Access แชร์ข้าม AWS Account ได้ง่ายผ่าน Resource-based Policy ที่ตัว Secret ซับซ้อนกว่า (ต้องใช้ Advanced Parameter หรือ Assume IAM Role)

1. แนวคิดสำคัญของ Infrastructure as Code (IaC)

Feynman Technique: Declarative vs Imperative และคำว่า Idempotency คืออะไร?

ลองนึกถึงเวลาเราขึ้นแท็กซี่ไปสนามบินสุวรรณภูมิ:
• Imperative (เชิงคำสั่งทีละขั้น - เช่น Bash Script / AWS CLI): เราต้องสั่งคนขับทุกแยก "พี่เลี้ยวซ้ายตรงนี้ ขับตรงไป 500 เมตร ขึ้นทางด่วน..." ถ้าถนนปิดตรงไหน สคริปต์จะพังทันที!
• Declarative (เชิงประกาศผลลัพธ์ - เช่น Terraform / CloudFormation): เราแค่บอกคนขับว่า "ไปสนามบินสุวรรณภูมิครับ" (บอกผลลัพธ์สุดท้ายที่ต้องการ) คนขับจะคำนวณเส้นทางและพาไปถึงที่หมายเอง!
• Idempotency (ความคงสภาพ): สมมติเราเขียนในโค้ดว่า "ฉันต้องการ S3 Bucket 1 ถังชื่อ my-logs" ไม่ว่าเราจะกดรันคำสั่งซ้ำ 1 ครั้ง หรือ 100 ครั้ง ระบบก็จะตรวจดูว่ามีถังนี้อยู่แล้ว และคงสภาพให้มีแค่ 1 ถังเท่าเดิมเสมอ (ไม่สร้างซ้ำเป็น 100 ถัง)

ปัญหา ClickOps (การกดสร้างผ่านหน้าเว็บด้วยมือ)

เสี่ยงต่อ Human Error ลืมติ๊กเปิด Encryption, สร้างระบบ Test กับ Prod ไม่เหมือนกัน และเมื่อโดนแฮกไม่สามารถสร้างระบบใหม่ขึ้นมาทดแทนได้ทันเวลา

Configuration Drift (ภาวะการตั้งค่าเพี้ยนจากโค้ด)

เกิดจากระบบถูกสร้างด้วย Terraform แต่ตอนดึกแอดมินแอบล็อกอินหน้าเว็บ AWS Console ไปแก้พอร์ต Security Group ด้วยมือ ทำให้ค่าจริงบน Cloud ไม่ตรงกับไฟล์โค้ด

2. เจาะลึกคำสั่ง Terraform Workflow ทั้ง 5 ขั้นตอน (พร้อมตัวอย่างการใช้งานจริง)

1. terraform init ขั้นตอนเตรียมความพร้อมโปรเจกต์ (Initialization)

หน้าที่: เป็นคำสั่งแรกสุดที่ต้องรันเสมอเมื่อเขียนโค้ดใหม่หรือโคลนโปรเจกต์มาจาก Git คำสั่งนี้จะอ่านไฟล์ .tf เพื่อดาวน์โหลด Provider Plugins (เช่น hashicorp/aws) มาเก็บในโฟลเดอร์ .terraform และเชื่อมต่อกับ Remote Backend (เช่น S3 สำหรับเก็บ State) 

$ terraform init              # เริ่มต้นโปรเจกต์ ดาวน์โหลดปลั๊กอิน AWS และตั้งค่า S3 Backend
$ terraform init -upgrade     # อัปเกรดเวอร์ชันของ Provider Plugins ให้ใหม่ล่าสุดตามเงื่อนไขที่กำหนด
$ terraform init -reconfigure # ตั้งค่าการเชื่อมต่อ Remote Backend ใหม่โดยไม่สนค่าแคชเดิม
2. terraform validate ขั้นตอนตรวจไวยากรณ์โค้ด (Syntax & Logic Check)

หน้าที่: ตรวจสอบว่าโค้ด HCL ที่เราเขียนมีวงเล็บปีกกาครบไหม พิมพ์ชื่อ Argument ผิดหรือเปล่า หรืออ้างอิงชื่อตัวแปรที่ไม่มีอยู่จริงหรือไม่ (ทำงานแบบ Offline ในเครื่อง ไม่ต้องต่ออินเทอร์เน็ตไปหา AWS) 

$ terraform fmt               # (แนะนำรันคู่กัน) จัดระเบียบย่อหน้าโค้ดให้สวยงามอัตโนมัติ
$ terraform validate          # ตรวจสอบไวยากรณ์ ถ้าถูกต้องจะขึ้น "Success! The configuration is valid."
3. terraform plan ขั้นตอนจำลองแผนการเปลี่ยนแปลง (Dry-Run / Execution Plan)

หน้าที่: นำโค้ดที่เราเขียนไปเปรียบเทียบกับไฟล์ terraform.tfstate และรีซอร์สจริงบน AWS เพื่อสรุปแผนให้เรารีวิวก่อนว่า ถ้าสั่งรันจริง จะมีอะไรถูกสร้าง (+) แก้ไข (~) หรือลบทิ้ง (-) บ้าง โดยยังไม่ทำการเปลี่ยนแปลงจริง 

$ terraform plan -out=tfplan.binary
# ตัวอย่างผลลัพธ์บนหน้าจอ:
#   + resource "aws_s3_bucket" "audit_logs"          (เครื่องหมาย + สีเขียว = จะสร้างใหม่)
#   ~ resource "aws_security_group" "web_sg"         (เครื่องหมาย ~ สีเหลือง = จะแก้ไขค่าเดิม)
#   - resource "aws_instance" "old_test_server"      (เครื่องหมาย - สีแดง = จะถูกทำลายทิ้ง!)
# Plan: 1 to add, 1 to change, 1 to destroy.
4. terraform apply ขั้นตอนสั่งสร้างและแก้ไขทรัพยากรจริงบน Cloud (Provisioning)

หน้าที่: ยิง API ไปยัง AWS เพื่อสร้าง แก้ไข หรือลบรีซอร์สจริงตามแผนที่ได้จากขั้น Plan เมื่อทำสำเร็จจะอัปเดตสถานะล่าสุดลงในไฟล์ terraform.tfstate 

$ terraform apply                    # รันและหยุดถามให้พิมพ์ยืนยันว่า "yes" ก่อนลงมือทำจริง
$ terraform apply tfplan.binary      # รันตามไฟล์แผนที่ล็อกไว้แล้วในขั้น plan (ปลอดภัยที่สุดใน CI/CD)
$ terraform apply -auto-approve      # รันทันทีโดยไม่ถาม "yes" (นิยมใช้ใน Automated Pipeline)
5. terraform destroy ขั้นตอนลบทำลายทรัพยากรทั้งหมด (Teardown / Cleanup)

หน้าที่: ลบรีซอร์สทั้งหมดที่ถูกจัดการภายใต้ State File นี้ออกไปจาก AWS อย่างสะอาดหมดจดตามลำดับ Dependency ย้อนกลับ เพื่อไม่ให้เสียค่าใช้จ่ายค้าง 

$ terraform destroy                                    # ลบทรัพยากรทั้งหมดในโปรเจกต์
$ terraform destroy -target=aws_instance.temp_worker   # ลบเจาะจงเฉพาะเซิร์ฟเวอร์ตัวที่ระบุตัวเดียว

คุณสมบัติ HashiCorp Terraform AWS CloudFormation (และ AWS CDK)
การรองรับคลาวด์ Multi-Cloud / Cloud Agnostic (ใช้ได้ทั้ง AWS, Azure, GCP, Cloudflare, Kubernetes) AWS Native เท่านั้น (สร้างทรัพยากรเฉพาะบน AWS)

ตัวอย่างโค้ด Terraform (main.tf) สร้าง S3 ที่ปลอดภัย
# 1. กำหนด Remote Backend เก็บ State บน S3 + ล็อกด้วย DynamoDB
terraform {
  backend "s3" {
    bucket         = "my-company-tfstate-vault"
    key            = "prod/network/terraform.tfstate"
    region         = "ap-southeast-1"
    encrypt        = true
    dynamodb_table = "terraform-state-locks"
  }
}

# 2. สร้าง S3 Bucket
resource "aws_s3_bucket" "secure_logs" {
  bucket = "corp-security-logs-2026"
}

# 3. บังคับเข้ารหัส AES-256 (Encryption at Rest)
resource "aws_s3_bucket_server_side_encryption_configuration" "enc" {
  bucket = aws_s3_bucket.secure_logs.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}

# 4. ปิดกั้น Public Access ทั้ง 4 ประตู
resource "aws_s3_bucket_public_access_block" "block_public" {
  bucket                  = aws_s3_bucket.secure_logs.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
ตัวอย่างโค้ด AWS CloudFormation (template.yaml) ที่ได้ผลลัพธ์เดียวกัน
AWSTemplateFormatVersion: '2010-09-09'
Description: 'Deploy a secured S3 bucket via CloudFormation'

Resources:

      BucketName: 'corp-security-logs-2026'

      BucketEncryption:

          - ServerSideEncryptionByDefault:
              SSEAlgorithm: AES256
      # ปิดกั้น Public Access ทั้ง 4 ประตู

        BlockPublicAcls: true
        BlockPublicPolicy: true
        IgnorePublicAcls: true
        RestrictPublicBuckets: true
      VersioningConfiguration:
        Status: Enabled

ไฟล์ terraform.tfstate เก็บโครงสร้างทั้งหมดของระบบ รวมถึงข้อมูลลับและรหัสผ่านฐานข้อมูลในรูปแบบข้อความธรรมดา (Plaintext)!
• ห้าม เอาไฟล์ .tfstate ขึ้น Git เด็ดขาด (ต้องใส่ใน .gitignore)
• ต้องเก็บไว้ใน Remote Backend บน Amazon S3 ที่เปิด KMS Encryption, เปิด S3 Versioning (เผื่อย้อนคืนไฟล์) และบล็อก Public Access

หัวข้อที่ 1

1. สถาปัตยกรรม Amazon VPC, การคำนวณ CIDR & 5 Reserved IPs

Feynman Technique: เข้าใจ VPC, Public Subnet, Private Subnet, IGW และ NAT Gateway ใน 1 นาที

ลองนึกว่า VPC คือ "อาณาจักรอาคารสำนักงานของบริษัทเรา":
• Public Subnet (ล็อบบี้ต้อนรับชั้น 1): เป็นโซนที่คนภายนอกเดินเข้ามาติดต่อได้โดยตรงผ่านประตูใหญ่หน้าตึกที่ชื่อว่า Internet Gateway (IGW) เราจึงวาง Web Server หรือ Load Balancer ไว้ที่นี่
• Private Subnet (ห้องนิรภัยชั้นใต้ดิน): เป็นโซนเก็บ Database และ App Server ห้ามคนภายนอกเดินเข้ามาเด็ดขาด! แต่ถ้าเซิร์ฟเวอร์ในห้องใต้ดินอยากโหลดอัปเดตแพตช์จากอินเทอร์เน็ต มันจะฝากตัวแทนที่ชื่อว่า NAT Gateway (ซึ่งต้องตั้งอยู่ในห้อง Public Subnet ชั้น 1 และมี Elastic IP) เป็นคนออกไปซื้อของข้างนอกกลับมาให้ โดยที่คนข้างนอกไม่สามารถเดินสวนกลับเข้ามาในห้องใต้ดินได้!

สูตรคำนวณจำนวน IP จาก CIDR Block

IPv4 มีทั้งหมด 32 บิต สูตรหาจำนวน IP ทั้งหมดคือ 2^(32 - Prefix) และจำนวน IP ที่ใช้งานได้จริงบน AWS คือ 2^(32 - Prefix) - 5

• /16 (เช่น 10.0.0.0/16): 2^(32-16) = 2^16 = 65,536 IPs
• /24 (เช่น 10.0.1.0/24): 2^(32-24) = 2^8 = 256 IPs (ใช้จริงได้ 251 IPs)
• /28 (เล็กสุดใน VPC): 2^(32-28) = 2^4 = 16 IPs (ใช้จริงได้ 11 IPs)

5 Reserved IPs ของ AWS (ทำไมต้องลบ 5 เสมอ?)

ตัวอย่างสำหรับ Subnet 10.0.1.0/24 ทาง AWS จะยึด IP 4 ตัวแรก และ 1 ตัวสุดท้ายไว้เสมอ:

  • 1. 10.0.1.0 : Network Address (หมายเลขประจำเครือข่าย)
  • 2. 10.0.1.1 : VPC Router (เราเตอร์ภายในของ AWS)
  • 3. 10.0.1.2 : AWS DNS Server (ตัวแปลงชื่อโดเมน)
  • 4. 10.0.1.3 : สำรองไว้สำหรับอนาคต (Future use)
  • 5. 10.0.1.255 : Network Broadcast Address (IP สุดท้ายของวง)

2. เปรียบเทียบเชิงลึก: Security Group (SG) vs. Network ACL (NACL)

Feynman Technique: คำว่า Stateful (จำสถานะได้) vs Stateless (จำสถานะไม่ได้) ต่างกันอย่างไร?

• Security Group คือบอดี้การ์ดส่วนตัวหน้าประตูห้อง (Stateful - ความจำดี): สมมติคุณอนุญาตให้เพื่อนเดินเข้าห้องมาได้ (Inbound Allow) ตอนที่เพื่อนคุยธุระเสร็จแล้วจะเดินออกจากห้องกลับบ้าน บอดี้การ์ดจำหน้าได้ว่า "อ๋อ คนนี้เข้ามาอย่างถูกต้องเมื่อกี้" จึงเปิดประตูให้ออกได้เลยอัตโนมัติ โดยไม่ต้องเช็กใบอนุญาตขาออกซ้ำ!
• Network ACL คือป้อมยามหน้าหมู่บ้านที่เปลี่ยนกะตลอดเวลา (Stateless - ความจำสั้น): ตอนรถวิ่งเข้าหมู่บ้าน ยามกะเช้าตรวจบัตรผ่านขาเข้า (Inbound Rule) แต่พอจะขับรถออกจากหมู่บ้าน ยามกะบ่ายจำไม่ได้ว่าคุณเคยเข้ามา จึงต้องตรวจใบอนุญาตขาออก (Outbound Rule บน Ephemeral Port) อีกรอบหนึ่งเสมอ!

คุณลักษณะ Security Group (SG) Network ACL (NACL)
ระดับการทำงาน ระดับ Instance / ENI (การ์ดแลนของเซิร์ฟเวอร์) ระดับ Subnet (ครอบคลุมทุกเครื่องในซับเน็ตนั้น)
การจำสถานะ (State) Stateful (ขาเข้าผ่าน ขาออกตอบกลับผ่านอัตโนมัติ) Stateless (ต้องเขียนกฎอนุญาตทั้งขาเข้าและขาออกแยกกัน)
ชนิดของกฎที่เขียนได้ เขียนได้เฉพาะ Allow Rules เท่านั้น (บล็อกเฉพาะเจาะจง IP ไม่ได้) เขียนได้ทั้ง Allow และ Deny Rules (ใช้แบน IP ผู้โจมตีได้!)
ลำดับการตรวจกฎ ประเมินกฎทุกข้อรวมกันทั้งหมดก่อนตัดสินใจ ประเมินเรียงตามเลข Rule Number (น้อยไปมาก) เจอข้อไหนตรงเงื่อนไขทำทันที

3. VPC Endpoints, AWS WAF, AWS Shield & Amazon GuardDuty

VPC Endpoints (เชื่อมบริการ AWS แบบไม่ผ่านเน็ตสาธารณะ)

ช่วยให้ EC2 ใน Private Subnet คุยกับบริการ AWS ได้โดยไม่ต้องมี NAT Gateway หรือออกเน็ต:

  • Gateway Endpoint (ฟรี!): ใช้ได้กับแค่ 2 บริการ คือ Amazon S3 และ DynamoDB (ทำงานผ่าน Route Table)
  • Interface Endpoint (AWS PrivateLink): สร้าง ENI พร้อม Private IP รองรับบริการ AWS แทบทั้งหมด เช่น KMS, Secrets Manager, SSM (มีค่าใช้จ่าย)
AWS WAF vs. AWS Shield (ป้องกันหน้าด่าน)
  • AWS WAF (Web Application Firewall): ป้องกันระดับ Layer 7 (HTTP/HTTPS) เช่นบล็อก SQL Injection (SQLi), Cross-Site Scripting (XSS), บล็อกประเทศ (Geo-blocking) และจำกัดจำนวนครั้งที่ยิงรัวๆ (Rate-based rule)
  • AWS Shield: ป้องกันการโจมตีแบบ DDoS (Layer 3/4) แบ่งเป็น Shield Standard (เปิดฟรีอัตโนมัติทุกบัญชี) และ Shield Advanced (จ่ายรายเดือน มีทีม DRT ช่วย 24/7 และคุ้มครองค่าใช้จ่ายที่พุ่งจาก DDoS)
Amazon GuardDuty (นักสืบ AI ตรวจจับภัยคุกคามอัจฉริยะ)

ใช้ Machine Learning วิเคราะห์ Log 3 แหล่งหลักโดยไม่ต้องติดตั้ง Agent คือ: 1. AWS CloudTrail Logs, 2. VPC Flow Logs, และ 3. DNS Query Logs (รวมถึง EKS Audit Logs, S3 Data Events) เพื่อตรวจจับพฤติกรรมแฮกเกอร์ เช่น แอบเอา EC2 ไปขุด Bitcoin, การเดารหัสผ่าน SSH Brute-force หรือการดูดข้อมูลออกจาก S3 ผิดปกติ

หัวข้อที่ 1

1. สถาปัตยกรรม Container Security & Container Hardening

Feynman Technique: Virtual Machine (VM) vs Container (Docker) ต่างกันอย่างไรในมุมความปลอดภัย?

• Virtual Machine (VM) เหมือน "บ้านเดี่ยวแยกหลัง": บ้านแต่ละหลังมีฐานราก ท่อน้ำ และระบบไฟแยกขาดจากกัน (มี Guest OS ของใครของมัน คั่นด้วย Hypervisor) ถ้าบ้านข้างๆ ไฟไหม้ บ้านเราก็ยังปลอดภัย แต่ข้อเสียคือสร้างช้าและกินพื้นที่มาก
• Container เหมือน "ห้องพักในคอนโดเดียวกัน": ทุกห้องสร้างเสร็จไวและเบาหวิว เพราะทุกห้องใช้โครงสร้างตึกและท่อน้ำหลักร่วมกัน ซึ่งเรียกว่า Shared Host OS Kernel! ความน่ากลัวคือ ถ้าห้องข้างๆ ได้สิทธิ์ผู้จัดการตึก (รัน Container ด้วยสิทธิ์ root หรือเปิดโหมด --privileged) แล้วเจาะผนังทะลุท่อน้ำหลักได้ มันจะยึดได้ทั้งตึกทันที! เหตุการณ์นี้เรียกว่า Container Breakout (Container Escape)

1. ห้ามรันด้วยสิทธิ์ Root (Enforce Non-Root User)

ใน Dockerfile ต้องใส่คำสั่ง USER appuser และห้ามรันแฟล็ก --privileged เด็ดขาด เพื่อป้องกัน Container Breakout

2. ใช้ Minimal / Distroless Base Images

ใช้ Image ขนาดเล็กที่มีเฉพาะไลบรารีที่จำเป็น (ไม่มี Shell หรือ Package Manager ให้แฮกเกอร์รันคำสั่ง) และทำ Multi-stage builds

3. สแกนช่องโหว่ด้วย Amazon ECR Image Scanning / Trivy

สแกนหาช่องโหว่ CVE ใน Container Image ทุกครั้งที่ Push ขึ้น Registry ก่อนนำไปรันจริง

4. ใช้ AWS Fargate (Serverless Container)

แยกแต่ละ Task/Pod ลงในสภาพแวดล้อม VM ขนาดจิ๋วที่แยกจากกัน (Firecracker MicroVM) และ AWS ดูแลแพตช์ Host OS ให้ทั้งหมด

2. DevSecOps Pipeline & Shift-Left Security (SAST vs SCA vs DAST)

Feynman Technique: ทำไมต้อง "Shift-Left" และแยก SAST, SCA, DAST อย่างไรไม่ให้จำสลับ?

เมื่อเขียนแผนผังพัฒนาซอฟต์แวร์จากซ้ายไปขวา: [เขียนโค้ด] ──▶ [Build] ──▶ [Test] ──▶ [ขึ้น Production]
สมัยก่อนเรารอให้แอปสร้างเสร็จแล้วค่อยให้ฝ่าย Security มาตรวจตอนท้ายสุด (ขวาสุด) พอเจอช่องโหว่ต้องรื้อเขียนใหม่แพงมาก! Shift-Left Security คือการดึงการตรวจความปลอดภัยมาไว้ฝั่งซ้ายสุดตั้งแต่ตอนโปรแกรมเมอร์กำลังพิมพ์โค้ด:
• SAST (Static = นิ่ง): ตรวจจาก "โค้ดดิบที่เราเขียนเอง" โดยไม่ต้องกดรันโปรแกรม เหมือนครูตรวจการบ้านจากสมุดพจน์
• SCA (Software Composition = ส่วนผสม): ตรวจ "ไลบรารีคนอื่นที่เราไปก๊อปมาใช้" (เช่น package.json, requirements.txt) ว่ามีของเน่าหรือติดช่องโหว่ CVE ไหม
• DAST (Dynamic = เคลื่อนไหว): รอให้โปรแกรมรันเป็นเว็บจริงก่อน แล้วจำลองตัวเป็นแฮกเกอร์ยิงเจาะจากข้างนอกเข้ามา

ประเภทการทดสอบ รูปแบบ (Box) สิ่งที่ตรวจสอบ ตัวอย่างเครื่องมือยอดนิยม
1. Secrets Scanning Pre-commit / Git สแกนหา API Keys, Passwords, AWS Keys ที่เผลอพิมพ์ติดในโค้ด TruffleHog, GitGuardian, Gitleaks
2. SAST (Static Application Security Testing) White-box (เห็นโค้ด) วิเคราะห์ Source Code ที่เขียนขึ้นเองเพื่อหาช่องโหว่โดยไม่ต้องรันแอป SonarQube, Semgrep, Checkmarx, CodeGuru
3. SCA (Software Composition Analysis) Dependency Scan ตรวจ Open-source Libraries / Packages ภายนอกเทียบกับฐานข้อมูล CVE Snyk, Dependabot, Trivy, OWASP Dependency-Check
4. IaC Scanning Config Scan ตรวจไฟล์ Terraform / CloudFormation ว่าตั้งค่าผิดหลัก Security หรือไม่ Checkov, tfsec, KICS
5. DAST (Dynamic Application Security Testing) Black-box (ยิงจากนอก) ยิงทดสอบแอปพลิเคชันที่กำลังรันอยู่จริงเพื่อหาช่องโหว่ตอนทำงาน OWASP ZAP, Burp Suite

3. Cloud Incident Response (NIST SP 800-61) & Cloud Forensics

สถานการณ์ออกสอบ: เมื่อตรวจพบว่า EC2 Instance ถูกแฮกเกอร์เจาะเข้ามา ต้องทำอย่างไร?

สิ่งที่ห้ามทำเด็ดขาด: ห้ามกด Stop, Reboot หรือ Terminate เครื่องทันที! เพราะหลักฐานของมัลแวร์ที่ซ่อนอยู่ในหน่วยความจำชั่วคราว (RAM / Volatile Memory) จะสลายหายไปทันทีเหมือนเอาน้ำล้างรอยนิ้วมือโจร!
ขั้นตอนที่ถูกต้องตามหลัก Cloud Forensics:
1. Containment (กักกันบริเวณ): เปลี่ยน Security Group ของ EC2 เครื่องนั้นให้เป็น Quarantine Security Group (ลบกฎ Inbound และ Outbound ออกทั้งหมด) และเปิด Termination Protection เพื่อป้องกันคนเผลอลบเครื่อง
2. Capture Volatile Data: ดึงข้อมูลจาก RAM และ Network Connections ที่ค้างอยู่เก็บไว้
3. EBS Snapshot Isolation: สั่งถ่ายสำเนาดิสก์ (Create EBS Snapshot) แล้วส่งไปเปิดวิเคราะห์ใน Isolated Forensics VPC / Forensics AWS Account แยกต่างหาก เพื่อไม่ให้หลักฐานต้นฉบับแปดเปื้อน

1. Preparation

เปิด CloudTrail/Logs รอไว้ล่วงหน้า เตรียมคู่มือ Playbook, Quarantine SG และซ้อม GameDays

2. Detection & Analysis

รับแจ้งเตือนจาก GuardDuty/Security Hub วิเคราะห์ขอบเขตความเสียหายและเวลาที่เกิดเหตุ

3. Containment, Eradication & Recovery

บล็อกเน็ตเครื่องที่ติดเชื้อ ถอนสิทธิ์ IAM Key ที่รั่ว กำจัดช่องโหว่ และรันเครื่องใหม่จาก Golden AMI

4. Post-Incident Activity
