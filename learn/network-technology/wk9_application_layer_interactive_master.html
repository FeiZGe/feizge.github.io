Section 1

หลักการของโปรแกรมประยุกต์บนเครือข่าย (Principles of Network Applications)

Application Layer ทำหน้าที่เชื่อมต่อกับผู้ใช้โดยตรง แอปพลิเคชันจะสื่อสารผ่านปลายทาง (End Systems) 3 สถาปัตยกรรมหลัก ได้แก่ Client-Server, Pure P2P และแบบผสมผสาน (Hybrid)

🏢 Client-Server
  • Server: Always-on host, มี Permanent IP address, ขยายขนาดด้วย Server farms
  • Client: ติดต่อไปหา Server, เปิดปิดไม่แน่นอน, IP เปลี่ยนแปลง (Dynamic IP), ไคลเอนต์ไม่คุยกันเองตรงๆ
🤝 Pure P2P
  • ไม่มี Always-on server กลาง
  • Arbitrary end systems สื่อสารกันตรงๆ (Direct communicate)
  • Peers มี Dynamic IP และเข้าออกไม่แน่นอน
  • ข้อดี: Highly scalable (แชร์ยิ่งเยอะยิ่งเร็ว)
  • ข้อจำกัด: Difficult to manage & security
  • ตัวอย่างในสไลด์: Gnutella
⚡ Hybrid
  • Napster / BitTorrent:
    - File transfer เป็น P2P ("ไฟล์ไหนคนมีเยอะ ไฟล์นั้นจะโหลดเร็ว")
    - File search ทำแบบ Centralized (Peers ค้นหาไฟล์ที่ Server กลาง)
  • Instant Messaging:
    - Chatting คุยตรง P2P
    - Presence / Location ค้นหาว่าเพื่อนออนไลน์ที่ IP ไหนผ่าน Central server

Pure P2P: เหมือน "เด็กๆ สลับการ์ดพลังกันเองในห้องเรียน" ทุกคนมีของแบ่งกันเล่นเอง ไม่ต้องมีครูมานั่งคุม

Section 2

ระบบชื่อโดเมน (DNS: Domain Name System) & การโจมตี DNS

DNS ทำหน้าที่แปลง Hostname (เช่น www.google.com) ให้เป็น IP Address เพื่อใช้ในการสื่อสาร เป็น Distributed Database ลำดับชั้น และเป็น Application-layer protocol (ความซับซ้อนอยู่ที่ขอบเครือข่าย / Edge)

1. Root DNS

เซิร์ฟเวอร์ราก 13 จุดเชิงตรรกะทั่วโลก ชี้ทางต่อไปยัง TLD

2. TLD Servers

ดูแลนามสกุลระดับบนสุด เช่น .com, .org, .net, .th, .edu

3. Authoritative

เซิร์ฟเวอร์ต้นสังกัดขององค์กร รู้ IP จริงของเครื่องปลายทาง

4. Local DNS

อยู่ใกล้ Client (ที่ ISP หรือ มหาวิทยาลัย) คอยแคชข้อมูลคำตอบ

🛡️ การโจมตี DNS (Attacking DNS - Slide 18)

💥 DDoS Attacks

  • Bombard root servers with traffic: ไม่ค่อยสำเร็จในอดีตจนถึงปัจจุบันเนื่องจากมี Traffic Filtering และ Local DNS servers มีการ Cache IP ของ TLD servers ไว้แล้ว จึงสามารถบายพาส Root server ได้
  • Bombard TLD servers: ยากที่จะโจมตี Root ส่วนใหญ่จะโดนที่ TLD ซึ่งอาจสร้างผลกระทบและอันตรายได้รุนแรงกว่า (Potentially more dangerous)

🎭 Redirect Attacks

  • Man-in-the-middle: ดักจับการสืบค้นข้อมูล (Intercept queries) เพื่อดักแปลงผลลัพธ์
  • DNS Poisoning (Cache Poisoning): คนร้ายส่งข้อมูลตอบกลับปลอม (Send bogus replies) ไปยัง DNS server เพื่อหลอกให้แคช IP ปลอม เมื่อเหยื่อขอเว็บจริง จะถูกส่งไปเว็บหลอกลวง (Fake website) ทันที

Section 3

เว็บและโปรโตคอล HTTP (HTTP 1.0 vs 1.1, Cookies)

HTTP (HyperText Transfer Protocol) ทำงานบนโมเดล Client/Server ผ่าน TCP โดยมีวิวัฒนาการสำคัญระหว่าง HTTP 1.0 และ 1.1 รวมถึงการจัดการสถานะ (State) ด้วย Cookies

HTTP/1.0 (RFC 1945) Nonpersistent HTTP
  • At most one object is sent over a single TCP connection.
  • ส่งเสร็จ 1 ไฟล์ ปิดการเชื่อมต่อทันที (Close connection)
  • ถ้าเว็บมี HTML 1 ไฟล์ + รูปภาพ 10 รูป ต้องเปิด-ปิด TCP ใหม่ทั้งหมด 11 ครั้ง!
  • เสียเวลา Overhead จาก 3-way Handshake ทุกครั้ง (ช้ามาก)
HTTP/1.1 (RFC 2068) Persistent HTTP (Default)
  • Multiple objects can be sent over single TCP connection.
  • เปิด TCP 1 ครั้ง ท่อจะเปิดค้างไว้ แล้วดูดรูปภาพและไฟล์อื่น ๆ ต่อเนื่องได้ทันที
  • ลด RTT (Round-Trip Time) และประหยัดทรัพยากร CPU/Memory ของเซิร์ฟเวอร์มหาศาล

🍪 Cookies & User-Server Interaction (Slide 33)

Authorization:

เนื่องจาก HTTP เป็น Stateless ไคลเอนต์จึงต้องแนบข้อมูลยืนยันตัวตน (Authorization) ไปในทุกๆ คำขอเพื่อควบคุมการเข้าถึงเนื้อหา (Control access)

Cookies:

เว็บไซต์ใช้เพื่อติดตามและจำผู้ใช้งาน (Keep track of users) โดยเก็บไว้ที่ Browser เช่น: ตะกร้าสินค้าออนไลน์, รักษาสถานะล็อกอิน, และระบบแนะนำสินค้าตามพฤติกรรม

HTTP/1.0: โทรสั่งพิซซ่า พอพนักงานรับแล้ววางสายทันที แล้วคุณต้องโทรไปใหม่เพื่อสั่งโค้ก แล้วโทรใหม่อีกสายเพื่อสั่งไก่ทอด (เหนื่อยและเสียเวลาโทร)

HTTP/1.1: โทรสายเดียว คุยต่อยาวๆ "ขอพิซซ่า โค้ก ไก่ทอด ด้วยครับ" ส่งครบในสายเดิม

Cookies: ตราปั๊มข้อมือตอนเข้าสวนสนุก เจ้าหน้าที่ไม่ต้องจำหน้าคุณ แค่คุณยื่นข้อมือที่มีตราปั๊มก็เดินเข้าเล่นได้ทันที

SMTP (RFC 5321)

ใช้ ส่ง (Push) และส่งต่อระหว่างเซิร์ฟเวอร์บน TCP พอร์ต 25 เป็นข้อความ ASCII โต้ตอบระหว่าง Client และ Server

POP (RFC 1939)

Post Office Protocol: ใช้ดาวน์โหลดเมลลงเครื่อง (Download-and-delete หรือ keep) ไม่ซิงก์โฟลเดอร์/สถานะข้ามเครื่อง

Section 5

การสตรีมมิงวิดีโอและ Content Distribution Networks (CDNs)

ทราฟฟิกวิดีโอครองแบนด์วิดท์มหาศาล (Netflix 37%, YouTube 16% ของเน็ตบ้าน) จึงต้องเผชิญกับความท้าทายเรื่อง Scale (ผู้ใช้ ~1 พันล้านคน) และ Heterogeneity (ความหลากหลายของอุปกรณ์และความเร็วเน็ต)

🎞️ Video Coding (การบีบอัดวิดีโอ - Slide 37)

  • Spatial Redundancy (ในภาพเดียวกัน): เช่น ท้องฟ้าสีม่วงกว้างใหญ่ แทนที่จะส่งค่าสีม่วง $N$ จุดซ้ำๆ ก็ส่งแค่ค่าสีม่วง 1 ครั้ง พร้อมตัวเลขจำนวนที่ซ้ำ ($N$)
  • Temporal Redundancy (ระหว่างเฟรม): แทนที่จะส่งเฟรมใหม่ $i+1$ ทั้งภาพ ให้ส่งเฉพาะ ความแตกต่าง (Differences) จากเฟรม $i$ (เช่น คนกำลังวิ่ง ฉากหลังนิ่งสนิท)

📊 CBR vs VBR (Slide 38)

  • CBR (Constant Bit Rate): อัตราบิตคงที่ คุณภาพจะแปรผันตามฉาก
  • VBR (Variable Bit Rate): อัตราบิตปรับเปลี่ยนตามความซับซ้อนของภาพเชิงพื้นที่และเวลา เพื่อรักษาคุณภาพให้เสมอกัน
  • มาตรฐานในสไลด์: MPEG-1 (1.5 Mbps), MPEG-2 DVD (3-6 Mbps), MPEG-4 Internet (< 1 Mbps)

🎛️ DASH (Dynamic, Adaptive Streaming over HTTP) & "Intelligence at Client"

ฝั่ง Server:
  • หั่นไฟล์วิดีโอออกเป็นหลายๆ ท่อน (Chunks)
  • แต่ละ Chunk ถูกเข้ารหัสไว้ที่หลายอัตราบิต (Different rates: 360p, 720p, 1080p, 4K)
  • สร้าง Manifest file ระบุ URL ของแต่ละ Chunk
ฝั่ง Client ("Intelligence at Client"):
  • WHEN: ขอ Chunk ถัดไปเมื่อไหร่ เพื่อไม่ให้บัฟเฟอร์ขาด (Starvation) หรือล้น (Overflow)
  • WHAT: เลือก Encoding rate ไหนตามแบนด์วิดท์ที่วัดได้ในขณะนั้น
  • WHERE: ขอ Chunk จาก URL Server โหนดไหนที่ใกล้หรือแบนด์วิดท์สูง
Enter Deep (เช่น Akamai)

ติดตั้งเครื่อง CDN ลึกเข้าไปใน Access Networks ของ ISP ใกล้ชิดผู้ใช้มากที่สุด (~1,700 จุดทั่วโลก)

Bring Home (เช่น Limelight)

รวมศูนย์ไว้เป็นคลัสเตอร์ขนาดใหญ่จำนวนน้อยแห่ง ใกล้จุดเชื่อมต่อแลกเปลี่ยนข้อมูล (PoPs - Point of Presence / IXP)

Section 6

โพรโทคอลสำหรับ Internet of Things (MQTT vs CoAP)

อุปกรณ์ IoT มีข้อจำกัดสูงด้านหน่วยความจำ แบตเตอรี่ และพลังประมวลผล (Constrained devices) จึงมีการออกแบบโปรโตคอลเฉพาะ 2 รูปแบบหลักตามสไลด์

MQTT TCP / Pub-Sub
  • OASIS Standard: ดูแลและกำหนดมาตรฐานโดย OASIS MQTT Technical Committee
  • Lightweight full-duplex: น้ำหนักเบา ส่งข้อความมาตรฐานแบบสองทิศทาง
  • Operate over TCP: มั่นใจได้เรื่องการส่งถึงด้วย TCP
  • Publish/Subscribe Architecture: สื่อสารผ่านคนกลางที่เรียกว่า Broker ผู้ส่งและผู้รับไม่จำเป็นต้องรู้จักกัน
  • Small code footprint: เหมาะกับอุปกรณ์ขนาดเล็ก กินหน่วยความจำต่ำ
CoAP (Constrained Application Protocol) UDP / RESTful
  • HTTP for constrained devices: ออกแบบให้เหมือน HTTP เวอร์ชันย่อส่วน
  • Operate over UDP: ลด Overhead การสร้างท่อเชื่อมต่อ TCP
  • RESTful Architecture: ใช้คำสั่งคุ้นเคย 4 อย่าง: GET, POST, PUT, DELETE
  • 1-Byte Response Code: บีบอัดรหัสตอบกลับ (เช่น 200 OK, 404) เหลือเพียงขนาด 1 ไบต์
  • CoAP-to-HTTP Proxy: สามารถแปลงและเชื่อมต่อเข้า Web Server ปกติได้ง่าย
คุณลักษณะ (Feature) MQTT CoAP
Transport Protocol TCP UDP
สถาปัตยกรรม (Architecture) Publish / Subscribe (มี Broker) Request / Response (RESTful)
คำสั่งที่ใช้ Publish, Subscribe, Topic GET, POST, PUT, DELETE
ขนาด Response Code โครงสร้างโปรโตคอลปกติ บีบอัดเหลือ 1 Byte
องค์กรมาตรฐาน OASIS IETF

🧠 สิ่งที่ควรจำ (Exam Essentials)
  • MQTT ทำงานบน TCP สถาปัตยกรรมแบบ Publish/Subscribe ผ่าน Broker (OASIS standard)
  • CoAP ทำงานบน UDP สถาปัตยกรรมแบบ RESTful (GET, POST, PUT, DELETE)
  • CoAP บีบอัดรหัสตอบกลับ (Response Code) เหลือเพียง 1 Byte
🐣 Trick ELI5 (เล่าให้เด็ก 5 ขวบฟัง)

MQTT: เหมือนกลุ่ม LINE ของห้องเรียน มีหัวหน้าห้อง (Broker) คอยกระจายข่าว ใครอยากรู้เรื่องการบ้านก็กดเปิดแจ้งเตือนไว้ พอมีการบ้านส่งมา ก็เด้งเตือนทุกคนที่ติดตามทันที

CoAP: เหมือนเด็กส่งสารขี้เกียจพูดเยอะ วิ่งเร็วๆ ไม่รอเซ็นรับของ (UDP) และเวลาตอบคำถามไม่ยอมพูดเป็นคำ แต่ชู 1 นิ้ว (1 Byte) แทนคำว่า "โอเคเรียบร้อย"
