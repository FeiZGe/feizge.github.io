UDP: เร็ว เบา ไม่รับประกัน

Connectionless datagram — ไม่ handshake, ไม่มี ACK, ไม่ retransmit, ไม่ตรวจลำดับ, ไม่มี flow/congestion control Header มีแค่ 4 ฟิลด์ (รวม 8 ไบต์): Src port Dst port Length Checksum (ค่าเริ่มต้นครอบคลุม header, data เป็น optional ตามสไลด์)
ทำไมยังต้องมี UDP: แอปที่ไม่ต้องการความน่าเชื่อถือ หรือจัดการเองได้ เช่น streaming เสียง/วิดีโอสด (ช้ากว่าดีกว่าหยุดรอ), DNS (คำถามเดียวตอบเดียว handshake เสียเวลา), DHCP, NTP, CoAP, QUIC (HTTP/3)
ข้อเสีย: ส่งเร็วเกินไป receiver ล้นได้ (ไม่มี flow control), ถ้าทุกคนใช้ UDP ส่งไม่ยั้ง เครือข่ายล่มได้ (ไม่มี congestion control)

TCP: ช้ากว่าแต่ครบ

Connection-oriented + reliable (ACK, checksum, sequence number, retransmit หลัง timeout, จัดลำดับใหม่) + flow control (sliding window) + congestion control

Handshake

Client(active) Server(passive) SYN, seq=x ───────► ◄─────── SYN+ACK, seq=y, ack=x+1 ACK, ack=y+1 ───────► → ESTABLISHED ทำไมต้อง 3 ทาง: ทั้งสองฝั่งต้องตกลง initial sequence number และยืนยันว่าส่งได้ทั้งสองทิศ (ถ้า 2 ทาง server ไม่รู้ว่า client ได้รับ SYN+ACK จริงไหม)

Sliding Window และ Flow Control

ไบต์ถูกแบ่งเป็น 4 โซน: ACK แล้ว | ส่งแล้วรอ ACK (outstanding) | ส่งได้เลย | ยังส่งไม่ได้ ขนาดช่อง outstanding + ส่งได้เลย = window ที่ผู้รับ "ประกาศ" (advertise) ใน header
throughput ≈ Window / RTT (จนกว่าจะถึงความจุลิงก์) เต็มท่อเมื่อ Window ≥ Bandwidth × RTT (= BDP, Bandwidth-Delay Product)
สไลด์: (1) ถ้า RTT > เวลาส่งทั้ง window ส่งเสร็จแล้วต้อง รอ ACK ว่าง (ลิงก์ไม่เต็ม) (2) ถ้า RTT = เวลาส่ง window ACK มาต่อเนื่อง ส่งได้ไม่หยุด
ต่างจาก selective repeat: TCP ใช้ cumulative ACK (มี SACK เป็น option เสริม)
ELI5: window = จำนวนจานที่พนักงานวางบนโต๊ะลูกค้าได้โดยยังไม่เก็บ ลูกค้า (receiver) บอกว่า "โต๊ะฉันวางได้ 4 จาน" ถ้าพนักงานเดินไปครัวไกล (RTT สูง) แต่วางได้แค่ 4 จาน ลูกค้าจะนั่งว่าง
▸ ข้อ 3.1 Advertised Window คืออะไร (ข้อสอบจริง) แนวตอบ: เป็นค่า window size ที่ผู้รับ (receiver) ระบุใน TCP header ของ ACK เพื่อบอกผู้ส่งว่ายังมีพื้นที่ buffer รับข้อมูลได้อีกกี่ไบต์ ผู้ส่งต้องมีข้อมูลที่ส่งแล้วยังไม่ถูก ACK ไม่เกินค่านี้ เพื่อ ป้องกัน receiver buffer ล้น (flow control)
ส่วนเสริมที่ได้คะแนนเพิ่ม: ผู้ส่งใช้ Window = min{Advertised window, cwnd} คือส่งตามคอขวดที่ช้ากว่าระหว่างผู้รับกับเครือข่าย
โจทย์ที่อาจถูกปรับ
▸ Advertised window = 0 เกิดอะไรผู้ส่งหยุดส่งข้อมูล และส่ง zero-window probe เป็นระยะ จนผู้รับเคลียร์ buffer แล้วประกาศ window ใหม่
▸ เพิ่ม window เป็น 2 เท่า throughput เปลี่ยนไหมถ้า window/RTT ยังต่ำกว่าความจุลิงก์ → throughput เพิ่มเป็น 2 เท่า แต่เมื่อ window ≥ BDP แล้ว คอขวดคือ bandwidth เพิ่มอีกก็ไม่ได้อะไร (ส่วนเกินไปรอใน queue → delay เพิ่ม)
▸ ทำไม handshake ต้องมี seq ตั้งต้นสุ่ม / ถ้าไม่มี ACK ของ SYN+ACKseq สุ่มลดโอกาสสับสนกับ segment เก่าที่ค้างในเครือข่าย และกัน spoofing ง่าย ๆ; ถ้าไม่มี ACK สุดท้าย server ไม่รู้ว่า client พร้อมจริง → เกิด half-open connection
▸ UDP: checksum ผิดเกิดอะไร / ทำไม DNS ใช้ UDPผู้รับทิ้ง datagram เงียบ ๆ (ไม่มีการขอส่งใหม่ ถ้าต้องการแอปต้องทำเอง) DNS ใช้ UDP เพราะ query-response เล็ก เร็ว ประหยัด handshake ถ้าไม่ตอบแอปส่งซ้ำเอง
▸ TCP vs UDP ต่างกันอย่างไร (ตอบ 3 ข้อ)connection (handshake vs ไม่มี) / reliability (ACK+retransmit+ลำดับ vs ไม่มี) / control (flow+congestion vs ไม่มี) / header (20+ B vs 8 B) / ตัวอย่างแอป
ควรรู้เพิ่ม (ถ้าอยากเชื่อมกับ Security): SYN flood = ส่ง SYN รัว ๆ โดยไม่ตอบ ACK ทำให้ server ค้าง SYN_RCVD เต็มตาราง ป้องกันด้วย SYN cookies; RST injection ปิด connection ของคนอื่น; UDP amplification (DNS/NTP ตอบใหญ่กว่า query + spoof source IP) — เป็นเรื่องคลาสสิกใน SOC

ข้อ 1: กราฟ Sampled RTT และ RTO

คำศัพท์

  • RTT (Round-Trip Time) เวลาจากส่ง segment จนได้ ACK กลับ SampleRTT = ค่าที่วัดได้แต่ละรอบ (แกน y ของกราฟ)
  • EstimatedRTT ค่าเฉลี่ยถ่วงน้ำหนักของ sample (เส้นแนวโน้ม) Deviation ค่าเบี่ยงเบน (ความผันผวน)
  • RTO (Retransmission TimeOut) เวลาสูงสุดที่รอ ACK ถ้าหมดเวลา → ถือว่า packet หาย → ส่งใหม่ + ลด cwnd
  • Guard band = ส่วนที่ RTO เกิน EstimatedRTT เผื่อความผันผวน

อ่านกราฟในข้อสอบ

แกน x = Transmission Round (48 รอบ) แกน y = RTT (ms) อ่านได้ว่า ต่ำสุด 3 ms, สูงสุด 7 ms, ค่าเฉลี่ย ≈ 5 ms แกว่ง ±2 ms เสมอ "ตัวเลขที่ RTO ต้องเทียบ" คือ ค่าสูงสุดของกราฟ (7) ไม่ใช่ค่าเฉลี่ย เพราะ timeout ขึ้นถ้า sample > RTO เส้น RTO ที่วาดแนวนอนอยู่ต่ำกว่าจุดไหน จุดนั้นคือ timeout เกิน
ELI5: RTO = เวลาที่คุณรอเพื่อนตอบแชท ปกติเพื่อนตอบใน 3–7 นาที (เฉลี่ย 5) ถ้าตั้งรอแค่ 3 นาที คุณจะทักซ้ำตลอดทั้งที่เพื่อนกำลังพิมพ์ (spam ทำให้เพื่อนยิ่งช้า) ถ้ารอ 8 นาที ไม่ทักซ้ำผิดเลย แต่ถ้าแชทหลุดจริง คุณเสียเวลารอฟรีเกือบ 8 นาที

สูตร

อัลกอริทึมเดิม (สไลด์) EstimatedRTT_k = α·EstimatedRTT_(k-1) + (1-α)·SampleRTT (α ≈ 0.8–0.9) RTO = 2 × EstimatedRTT จุดอ่อน: ถือว่า variance คงที่ แต่จริง ๆ load สูง → variance พุ่ง อัลกอริทึมใหม่ (รวม variance) Difference = SampleRTT − EstimatedRTT EstimatedRTT += δ · Difference (δ = 1/8) Deviation += δ · ( |Difference| − Deviation ) RTO = μ · EstimatedRTT + φ · Deviation (μ = 1, φ = 4) ตัวอย่างคำนวณ: Est=5, Dev=1, ได้ sample=7, δ=1/8 → Diff=2 → Est=5.25 → Dev=1+⅛(2−1)=1.125 → RTO = 5.25 + 4×1.125 = 9.75 ms
Karn's algorithm: ถ้า segment ถูกส่งซ้ำ แล้วได้ ACK มา ไม่รู้ว่า ACK ตอบ "ครั้งแรก" หรือ "ครั้งที่สอง" → ไม่เอามาอัปเดต EstimatedRTT และ เพิ่ม RTO เป็น 2 เท่า (exponential backoff) จนกว่าจะได้ ACK ของ segment ที่ไม่ถูกส่งซ้ำ
▸ 1.1 RTO คงที่ = 3 ms จะเกิดอะไรขึ้น แนวตอบ: ทุก sample ที่ > 3 ms (ประมาณ 43 จาก 48 รอบ ≈ 90%) จะหมดเวลาก่อน ACK มาถึง ทั้งที่ packet ไม่ได้หาย → premature/spurious timeout → ผู้ส่งส่ง segment ซ้ำโดยไม่จำเป็น
ผลกระทบ: (1) เปลือง bandwidth ด้วย duplicate (2) ทำให้ congestion หนักขึ้น → RTT ยิ่งสูง → timeout มากขึ้นอีก (positive feedback / congestion collapse) (3) TCP ตีความว่าแออัด ลด cwnd ครึ่งหนึ่งและกลับสู่ slow start → throughput ตกมาก
▸ 1.2 RTO = 8 ms จะเกิดอะไรขึ้น แนวตอบ: 8 ms มากกว่า sample สูงสุด (7 ms) → ไม่มี spurious timeout เลย แต่เมื่อ packet หายจริง ผู้ส่งต้องรอเต็ม 8 ms (≈ 1.6 เท่าของ RTT เฉลี่ย 5 ms) ก่อนส่งใหม่ → ช่วงที่รอ window ไม่ขยับ ผู้ส่งว่าง throughput ลด/latency เพิ่ม สรุป: ปลอดภัยแต่ตอบสนองต่อการสูญหายช้า
▸ 1.3 อธิบายวิธีกำหนด RTO ที่ดี แนวตอบ: ควรเป็นค่า adaptive ไม่ใช่ค่าคงที่: (1) วัด SampleRTT ทุกรอบ แล้วคำนวณ EstimatedRTT ด้วย moving average (2) คำนวณ Deviation เพื่อวัดความผันผวน (3) ตั้ง RTO = EstimatedRTT + 4×Deviation (เผื่อ guard band ให้ครอบคลุมเกือบทุก sample ลด false timeout โดยไม่รอนานเกิน) (4) ใช้ Karn's algorithm เมื่อส่งซ้ำ (ไม่อัปเดต, ทวี RTO) ผลคือ RTO ตามสภาพเครือข่าย (เมื่อ load/variance ขึ้น RTO ขึ้นเอง)
โจทย์ที่อาจถูกปรับ
▸ RTO = 5 ms (ค่าเฉลี่ย) เกิดอะไรประมาณครึ่งหนึ่งของรอบ (sample 6 และ 7) จะ timeout ก่อน → เห็นผลแบบ 1.1 แต่เบากว่า สรุปว่า "RTO = ค่าเฉลี่ย" ไม่พอ ต้องบวก guard band (ลองเลื่อน slider ดูตัวเลขจริง)
▸ ถ้า φ (ตัวคูณ Deviation) เพิ่ม / ลดเพิ่ม → RTO กว้างขึ้น false timeout ลดแต่ตรวจ loss ช้าลง; ลด → RTO ชิดค่าเฉลี่ย ตอบสนองไว แต่ spurious timeout เพิ่ม (ลองลาก φ ไป 0 ใน Lab)
▸ ถ้า δ (หรือ α ในสูตรเดิม) เปลี่ยนδ มาก (α น้อย) → Estimated ตามค่าล่าสุดไว แต่กระตุก; δ น้อย (α มาก) → เรียบแต่ตามการเปลี่ยนเส้นทาง/แออัดไม่ทัน
▸ เส้นทางเปลี่ยน RTT จาก 5 กระโดดเป็น 15 ms ทันทีEst ยังเป็น ~5 → RTO เก่าต่ำเกิน ช่วงแรกเกิด spurious timeout → Karn ทวี RTO จนครอบ 15 ms หรือหลายรอบ Est จะตาม (ยิ่ง δ มากยิ่งไว)
▸ ทำไมต้องไม่วัด RTT จาก segment ที่ส่งซ้ำRetransmission ambiguity: ไม่รู้ว่า ACK ตอบ segment แรกหรือซ้ำ จะวัดสั้นเกิน (ถ้า ACK ของรอบแรกมาช้า) หรือยาวเกิน ทำให้ Est เพี้ยน
▸ ทำไม variance โตเร็วเมื่อ load สูงqueue ใน router ยาวขึ้นแบบไม่เป็นเส้นตรง (ดูกราฟ queueing delay vs load) ใกล้เต็มความจุ delay แกว่งแรง จึงต้องมี Deviation ในสูตร ไม่ใช่ใช้ 2×Est

Congestion Control & Avoidance

ELI5: เหมือนเปิดก๊อกน้ำเติมถัง ไม่รู้ว่าท่อรับได้เท่าไร: เริ่มเปิดนิดเดียว แล้วเร่งเป็นเท่าตัวจนใกล้ที่ท่อเริ่มล้น (slow start ไม่ได้ช้าจริง ชื่อมาจาก "เริ่มต่ำ") จากนั้นค่อย ๆ เพิ่มทีละนิด (congestion avoidance) พอน้ำล้น (packet loss) ก็ลดแรงครึ่งหนึ่ง แล้วค่อย ๆ เพิ่มใหม่ → กราฟฟันเลื่อย (sawtooth)

แนวคิด

  • Congestion = ข้อมูลเข้า router เกินกำลังส่งออก queue ยาว → delay สูง → ล้น → drop (เกิดได้หลายสเกลเวลา: packet ชนกัน µs, flows เต็มลิงก์ วินาที, ชั่วโมงเร่งด่วน)
  • TCP เป็น host-based, feedback-based, window-based: ส่งแล้วดูเหตุการณ์ (loss) ว่าเครือข่ายแออัดไหม
  • Window = min{Advertised window, cwnd} — flow control (ผู้รับ) vs congestion control (เครือข่าย)
  • Power = Load/Delay จุดโหลดที่ power สูงสุด = "optimal load" (knee ของกราฟ) ส่งเกินจุดนี้ delay พุ่งแต่ throughput แทบไม่เพิ่ม

กลไกของ cwnd

  1. Slow start: เริ่ม cwnd=1 เพิ่มแบบทวีคูณ (ทุก ACK += 1 → ทุก RTT ×2: 1,2,4,8…) ตราบที่ cwnd < ssthresh
  2. Congestion avoidance: เมื่อ cwnd ≥ ssthresh เพิ่มแบบเชิงเส้น (+1 ต่อ RTT) = Additive Increase
  3. เมื่อ loss: Multiplicative Decrease ssthresh = cwnd/2 • แบบ timeout: cwnd = 1 แล้ว slow start ใหม่ (หนัก เพราะแสดงว่าแออัดมาก)
  4. Fast retransmit: ได้ 3 duplicate ACK → ส่งซ้ำทันทีไม่รอ timeout Fast recovery: cwnd = ssthresh (ครึ่งหนึ่ง) ข้าม slow start ไปต่อที่ congestion avoidance (Reno) — Tahoe ยังกลับไป cwnd=1

Congestion Avoidance (ป้องกันก่อนเกิด)

TCP ธรรมดา "ตอบสนองหลังแออัดแล้ว" ระบบจึงแกว่งและแทบไม่เสถียร ทางเลือกคือป้องกันก่อน:
  • DECbit (router บอกชัดเจน): router ตั้งบิต DECbit ใน header ถ้า average queue ≥ 1 packet → ปลายทางคัดลอกบิตใส่ ACK → ผู้ส่งนับสัดส่วน packet ที่ถูกตั้งบิตใน 1 window: <50% → เพิ่มแบบ additive, ≥50% → ลดแบบ multiplicative
  • RED (router บอกโดยปริยาย ด้วยการ drop) → หน้าถัดไป
  • Host-based: ผู้ส่งดู RTT ที่เพิ่มขึ้นเป็นสัญญาณแออัด
Global synchronization: ถ้า drop พร้อมกันหลาย flow ทุกคนลด cwnd พร้อมกัน แล้วเพิ่มพร้อมกัน ลิงก์ว่างสลับล้นเป็นคลื่น RED สุ่ม drop ทำให้ flow ไม่ลดพร้อมกัน (desynchronize) ภาพรวมเรียบกว่า

ข้อ 2: Random Early Detection (RED)

ELI5: ร้านอาหารคิวยาว เจ้าของไม่รอให้คิวล้นร้านแล้วไล่ทุกคนกลับพร้อมกัน แต่เริ่ม "ขอให้ลูกค้าบางคนมาใหม่" ตั้งแต่คิวเริ่มยาว คิวยิ่งยาวยิ่งขอบ่อย ลูกค้าที่ถูกขอจะเดินช้าลง (ลด cwnd) คิวเลยไม่ล้น
แนวคิด: router drop packet แบบสุ่มก่อนที่ queue จะเต็ม โดยความน่าจะเป็น drop เพิ่มตาม average queue length (AvgLen) เป็นการบอก TCP โดยอ้อม (implicit) ว่ากำลังแออัด พัฒนามาจาก DECbit AvgLen(n+1) = (1 − w)·AvgLen(n) + w·Length(n) ← moving average (EWMA) AvgLen < minTh → p = 0 (ไม่ drop) minTh ≤ AvgLen < maxTh → p̂ = maxP · (AvgLen − minTh) / (maxTh − minTh) AvgLen ≥ maxTh → p = 1 (drop ทั้งหมด) Pr(drop) = p̂ / (1 − count·p̂) count = จำนวน packet ที่ผ่านมาตั้งแต่ drop ล่าสุด ข้อสอบนิยาม P_Throughput = % packet ที่ผ่าน router = (1 − p) × 100%

แปลง hostname ↔ IP ใช้ UDP port 53 เป็น hierarchy: Root → TLD (.com, .th) → Authoritative • Recursive (resolver ทำให้จนจบ) vs Iterative (ถูกชี้ไปถามต่อ) • มี cache + TTL • Record: A (IPv4), AAAA (IPv6), CNAME (alias), MX (mail server), NS (name server)

Iterated query: server ที่ถูกถามตอบกลับว่า "ไม่รู้ชื่อนี้ ไปถาม server นี้ต่อ" (local DNS ไล่ถามเอง root → TLD → authoritative) • Recursive query: ผลักภาระการแปลงชื่อให้ server ที่ถูกถาม (โหลดหนัก)
Caching: server ใดรู้ mapping ก็ cache ไว้ หมดอายุตาม TTL TLD มักถูก cache ใน local server จึงไม่ค่อยต้องไปถึง root

IoT Protocols: MQTT และ CoAP

ELI5: IoT = อุปกรณ์เล็ก ๆ (เซ็นเซอร์, หลอดไฟ) ที่แบตน้อย หน่วยความจำน้อย เน็ตไม่เสถียร จึงต้องใช้โปรโตคอลเบากว่า HTTP • MQTT = กลุ่มไลน์ที่มีแอดมิน (broker) ใครอยากรู้เรื่องไหนก็ "ติดตามห้อง" ใครมีข่าวก็โพสต์ห้องนั้น • CoAP = HTTP ฉบับย่อที่ใช้ได้กับของเล็ก ถามตรง ๆ ตอบตรง ๆ ผ่าน UDP

MQTT (Message Queuing Telemetry Transport)

  • รูปแบบ publish/subscribe ผ่าน broker กลาง ผู้ส่งกับผู้รับ ไม่รู้จักกัน (decoupled ทั้งเวลาและที่อยู่)
  • Topic เป็นลำดับชั้น เช่น home/livingroom/temp, wildcard + (1 ระดับ), # (หลายระดับ)
  • รันบน TCP port 1883 (8883 = TLS) header เล็กมาก (ขั้นต่ำ 2 ไบต์)
  • มี QoS 3 ระดับ: 0 = at most once (ส่งแล้วลืม), 1 = at least once (ACK, อาจซ้ำ), 2 = exactly once (handshake 4 ทาง ช้าสุดแต่ไม่ซ้ำ)
  • ฟีเจอร์: Retained message (broker เก็บค่าล่าสุดให้ subscriber ใหม่), Last Will (broker ประกาศเมื่ออุปกรณ์ขาด), Keep-alive, persistent session

CoAP (Constrained Application Protocol)

  • รูปแบบ request/response แบบ RESTful เหมือน HTTP: method GET/POST/PUT/DELETE, URI (/light), response code (เช่น 2.05 Content ≈ HTTP 200) → ตอบ "คล้าย HTTP"
  • รันบน UDP port 5683 header 4 ไบต์ จึงเบามาก แต่ ทำ reliability เองในโปรโตคอล
  • ชนิดข้อความ: CON (Confirmable ต้องมี ACK), NON (ไม่ต้อง ACK), ACK, RST
  • Message ID (mid) จับคู่ request–ACK และตรวจ duplicate; piggy-backed response = ตอบข้อมูลมาในแพ็กเก็ต ACK เลย
  • มี Observe (สมัครรับการเปลี่ยนแปลง) และ resource discovery (/.well-known/core)

รายละเอียดตามสไลด์: MQTT

เป็นโปรโตคอลแบบ lightweight full-duplex (OASIS standard) ออกแบบให้ code footprint เล็ก คิดค้นโดย Andy Stanford-Clark (IBM) และ Arlen Nipper ปี 1999 • v5.0 (2019): รองรับ scale, error reporting ดีขึ้น, request-response, user properties • ถ้า ไม่มี subscriber ที่ตรงกับ topic broker จะทิ้งข้อความ ถ้ามีหลายคนส่งให้ทุกคนที่ตรง (one-to-many)
Message format: fixed header บังคับ 2 ไบต์ + variable header (optional) + payload (optional) ใช้ optional น้อยเพื่อประหยัดบนเครือข่ายไร้สาย
Byte 1: [ Message Type (4 บิต) | DUP (1) | QoS Level (2) | RETAIN (1) ] Byte 2: Remaining Length (1–4 ไบต์: ความยาวส่วนที่เหลือ) Message Type: 1 CONNECT, 2 CONNACK, 3 PUBLISH, 4 PUBACK, 5 PUBREC, 6 PUBREL, 7 PUBCOMP, 8 SUBSCRIBE, 9 SUBACK, 10 UNSUBSCRIBE, 11 UNSUBACK, 12 PINGREQ, 13 PINGRESP, 14 DISCONNECT • DUP = ข้อความนี้อาจเคยส่งแล้ว (ส่งซ้ำ) • RETAIN = ให้ server เก็บข้อความล่าสุดไว้ส่งให้ subscriber ใหม่
ลำดับข้อความของ QoS:
• QoS 0 (fire and forget, at most once): Client → PUBLISH → Server → PUBLISH ไป Subscriber, Client ลบข้อความทันที
• QoS 1 (at least once): Client เก็บข้อความ → PUBLISH → Server เก็บ → ส่งต่อ subscriber → ลบ → PUBACK → Client ลบ (ถ้าไม่ได้ PUBACK ทันเวลา client ส่งซ้ำ จึงอาจซ้ำ)
• QoS 2 (exactly once): PUBLISH → PUBREC → PUBREL → PUBCOMP (4 ข้อความ ช้าสุด/เสียค่าข้อความเพิ่ม แต่ไม่ซ้ำไม่หาย)

ทุกผู้ใช้ใช้ความถี่เดียวกัน แต่ละคนมี chipping code เฉพาะ ถ้า code orthogonal ส่งพร้อมกันรบกวนกันน้อย encode : Z(i,m) = d(i) · c(m) (data × code) decode : D(i) = Σ Z(i,m)·c(m) / M (inner product ÷ M) ตัวอย่าง: code = (1,1,1,−1,1,−1,−1,−1) ส่ง d=−1 → ได้ −code; decode: (−1·8)/8 = −1 สัญญาณของผู้ส่งอีกคนที่ code orthogonal รวมแล้วตัดกันเป็น 0 • ต่างจาก FDMA (แบ่งความถี่) และ TDMA (แบ่งเวลา)

Registration และ Indirect routing

Registration: (1) มือถือเข้า visited network ติดต่อ FA (2) FA ติดต่อ HA แจ้ง "มือถือนี้อยู่ในเครือข่ายฉัน" ผลลัพธ์: FA รู้จักมือถือ, HA รู้ตำแหน่งมือถือ
Indirect routing: (1) correspondent ส่ง packet ไปที่ permanent address → ถึง home network (2) HA ดักจับ ห่อ (encapsulate) แล้วส่งไป COA ที่ FA (3) FA decapsulate ส่งให้มือถือ (4) มือถือ ตอบตรงถึง correspondent
ข้อสังเกต: มือถือใช้ 2 address: permanent (correspondent ใช้ → ตำแหน่ง transparent ต่อ correspondent) และ COA (HA ใช้) • ย้ายไป network ใหม่: ลงทะเบียน FA ใหม่ → FA ใหม่แจ้ง HA → HA อัปเดต COA → connection ต่อเนื่องได้ • ข้อเสีย triangle routing: เส้นทาง correspondent→home→mobile ไม่มีประสิทธิภาพ (โดยเฉพาะเมื่อ correspondent กับ mobile อยู่ network เดียวกัน)
Direct routing: correspondent ถาม HA เพื่อได้ foreign address (COA) แล้วส่งตรงถึง FA → แก้ triangle routing แต่ ไม่ transparent ต่อ correspondent และมีปัญหาถ้ามือถือย้าย network → แก้ด้วย anchor FA (FA แรก: ข้อมูลไปถึง anchor ก่อน แล้ว FA ใหม่ต่อสายโซ่ chaining)

Mobile IP (RFC 3344)

สามส่วน: indirect routing, agent discovery (agent advertisement = ICMP type 9 broadcast, มีบิต H/F บอกว่าเป็น home/foreign agent, บิต R = ต้องลงทะเบียน, ส่ง COA มาให้) และ registration with HA (registration request: COA, HA, MA, lifetime, identification → registration reply)

    โจทย์ที่อาจถูกปรับ
    ▸ เปรียบเทียบ indirect vs direct routing (ข้อดี-ข้อเสีย)Indirect: transparent ต่อ correspondent, ย้าย network ง่าย แต่ triangle routing • Direct: เส้นทางสั้น แต่ correspondent ต้องรู้ COA (non-transparent) และต้องใช้ anchor FA เมื่อย้าย
    ▸ Triangle routing คืออะไร เมื่อไรแย่สุดข้อมูลไป correspondent → home network → mobile ทั้งที่อาจอยู่ใกล้กัน แย่สุดเมื่อ correspondent กับ mobile อยู่ network เดียวกันแต่ home ไกล
    ▸ ถ้า HA ล่ม / FA ไม่ decapsulate เกิดอะไรHA ล่ม: ไม่มีใครส่งต่อ packet ที่ถูกส่งมาที่ permanent address → ติดต่อมือถือที่อยู่นอก home ไม่ได้; FA ไม่ decapsulate: packet ที่ห่ออยู่ถึงมือถือไม่ได้
    ▸ ทำไมต้องมี encapsulationpacket เดิมมี dest = permanent address (home) ถ้าส่งต่อตรง ๆ จะวนกลับ home จึงห่อซองใหม่ที่ dest = COA แล้วแกะที่ FA คืน packet เดิม
    ▸ HLR/VLR/MSRN คืออะไร ตรงกับอะไรใน Mobile IPดูตารางเปรียบเทียบข้างบน
    ▸ ย้ายไป foreign network ใหม่ ต้องเกิดอะไรลงทะเบียนกับ FA ใหม่ → FA ใหม่แจ้ง HA → HA อัปเดต COA → packet ถูกส่งต่อด้วย COA ใหม่ (ต่อเนื่อง)
