01 OSI Layering & Transport Layer

Transport layer (Layer 4) ทำหน้าที่ peer-to-peer communication — คือแม้ข้อมูลจะวิ่งผ่าน router หลายตัวในทาง physical แต่ในมุมของ transport layer มันคุยกันตรงๆ กับ transport layer อีกฝั่งเสมือนไม่มี router คั่นอยู่เลย

◆ ELI5

ลองนึกถึงการส่งจดหมายผ่านไปรษณีย์หลายทอด (network/link/physical layer คือคนขนส่ง) แต่ "เนื้อหาจดหมาย" ที่ผู้ส่งกับผู้รับคุยกัน (transport/application layer) เหมือนเขาคุยกันตรงๆ ไม่สนใจว่าจดหมายผ่านมือใครมาบ้าง — นี่คือ peer-layer communication

02 UDP — User Datagram Protocol

UDP คือ transport protocol ที่ เร็วแต่ไม่รับประกันอะไรเลย เหมาะกับงานที่ยอมรับการสูญเสียข้อมูลได้ ดีกว่าที่จะรอ

CONNECTIONLESS

ลักษณะของ UDP

  • ไม่มีการ "จับมือ" (handshake) ก่อนส่ง — ส่ง packet ได้ทันทีทุกเมื่อ
  • ไม่มี acknowledgement → ผู้ส่งไม่รู้ว่าข้อมูลถึงหรือไม่
  • checksum ครอบคลุมเฉพาะ header เท่านั้น (data เป็น optional)
  • ไม่มีกลไกตรวจจับ packet หาย หรือมาไม่เรียงลำดับ
  • ไม่มี automatic retransmission และไม่มี flow control → อาจ overrun ผู้รับได้

ทำไมยังต้องมี UDP?

  • แอปที่ไม่สนใจความน่าเชื่อถือ (reliable delivery ไม่จำเป็น)
  • แอปที่มีกลไกจัดการของตัวเองอยู่แล้ว เช่น streaming real-time audio/video (รอ retransmit ไม่ทันเวลา ก็ข้ามไปเลยดีกว่า)
  • ใช้ port number ในการ demultiplex ว่า packet ไหนเป็นของ app ไหน

03 TCP — ลักษณะพื้นฐาน & 3-Way Handshake

TCP ตรงข้ามกับ UDP โดยสิ้นเชิง: connection-oriented และ reliable — ทุกกลไกใน TCP มีไว้เพื่อรับประกันว่าข้อมูลไปถึงครบ ถูกลำดับ และไม่ทำให้เครือข่ายพัง

RELIABLE

กลไกความน่าเชื่อถือของ TCP

  • Acknowledgement — บอกว่าข้อมูลถึงแล้ว
  • Checksum — ตรวจจับข้อมูลเสีย
  • Sequence number — ตรวจจับข้อมูลหายหรือมาไม่เรียง
  • ข้อมูลเสีย → retransmit หลัง timeout
  • ข้อมูลมาไม่เรียง → เรียงใหม่ (re-sequence)
  • Flow control แบบ window-based → กันผู้รับ overrun
  • Congestion control → แบ่งปันความจุเครือข่ายอย่างเป็นธรรม

Connection Close — 2 × 2-Way Handshake

การปิด TCP ไม่ใช่การจับมือ 3 ขั้นเหมือนตอนเปิด แต่เป็นการปิดทีละทิศทาง (แต่ละฝั่งต้องบอกลาเอง) — client ส่ง FIN → server ตอบ ACK (และอาจส่งข้อมูลที่เหลือ) → จากนั้น server ส่ง FIN ของตัวเอง → client ตอบ ACK กลับ

◆ ELI5

3-way handshake เหมือนโทรศัพท์คุยกัน: "ได้ยินไหม?" (SYN) → "ได้ยิน แล้วคุณได้ยินฉันไหม?" (SYN+ACK) → "ได้ยิน เริ่มคุยได้เลย" (ACK) ทั้งสองฝั่งต้องยืนยันว่า "พร้อมรับ-พร้อมส่ง" ก่อนเริ่มคุยจริง ส่วนตอนวางสาย ต้องบอกลาทีละฝั่ง เพราะอาจมีฝั่งหนึ่งยังพูดไม่จบ (เช่นมีข้อมูลค้างส่งอยู่)

05 TCP Sliding Window

Sliding window ตอบคำถาม 3 ข้อ: (1) ผู้ส่งมีข้อมูล outstanding ในเครือข่ายได้เท่าไหร่ (2) เมื่อ error เกิดขึ้น ต้อง retransmit แค่ส่วนที่หายไปหรือทั้งหมด (3) จะไม่ overrun buffer ของผู้รับได้อย่างไร

Window มีความหมาย สำหรับฝั่งผู้ส่ง เท่านั้น — ขนาด window ปัจจุบันถูก "advertised" (ประกาศ) โดยผู้รับ ปกติเริ่มต้นที่ 4k–8k bytes ตอนตั้ง connection

RTT > Window size

ผู้ส่งต้องหยุดรอ ACK ก่อนจะส่งต่อ → throughput ถูกจำกัดโดย RTT ไม่ใช่ bandwidth จริง

RTT = Window size

ผู้ส่งส่งได้ต่อเนื่องพอดีกับจังหวะ ACK กลับมา → ใช้ bandwidth ได้เต็มที่ที่สุด

06 Timeouts & Retransmission (RTO)

การเลือกค่า RTO (Retransmission TimeOut) สำคัญมาก: ตั้งนานเกินไป → รอ retransmit นาน (สูญเวลา) ตั้งสั้นเกินไป → retransmit ทั้งที่ไม่จำเป็น (สิ้นเปลือง bandwidth และยิ่งซ้ำเติม congestion)

ALGORITHM V1 (Original)

สูตรดั้งเดิม

EstimatedRTTk = α·EstimatedRTTk-1 + (1-α)·SampleRTT
RTO = 2 × EstimatedRTT

ปัญหา: สมมติว่า variance คงที่ (ตัวคูณ 2 กำหนดตายตัว) แต่ในความเป็นจริง variance ของ delay จะยิ่งเพิ่มขึ้นเมื่อ load / congestion สูงขึ้น ทำให้ RTO ที่คำนวณได้ไม่เหมาะกับสภาพเครือข่ายจริง

ALGORITHM V2 (Jacobson/Karels)

สูตรใหม่ที่คิด variance เข้าไปด้วย

Difference = SampleRTT − EstimatedRTT
EstimatedRTTk = EstimatedRTTk-1 + (δ×Difference)
Deviation = Deviation + δ×(|Difference| − Deviation)
RTO = μ × EstimatedRTT + φ × Deviation   (μ≈1, φ≈4)

KARN'S ALGORITHM

ปัญหา: ประมาณ RTT ยังไงเมื่อมีการ retransmit?

ถ้า packet ถูกส่งซ้ำ แล้ว ACK กลับมา — เราไม่รู้ว่า ACK นี้ตอบรับการส่งครั้งแรกหรือครั้งที่ retransmit (เรียกว่า retransmission ambiguity) ถ้าคำนวณ RTT จากตรงนี้จะได้ค่าที่ผิด

ทางแก้: เมื่อมีการ retransmit — ห้ามอัปเดต EstimatedRTT จาก sample นั้น (แต่ยัง double RTO ไว้ก่อน เผื่อ network กำลังแออัดจริง)

RTO เหมือนการตั้งเวลาว่า "รอกี่นาทีถึงจะโทรถามซ้ำว่าทำไมยังไม่ตอบ" ถ้าตั้งนานไป เสียเวลาเปล่า ถ้าตั้งสั้นไป จะโทรกวนทั้งที่คนโน้นกำลังจะตอบอยู่แล้ว (แถมยิ่งโทรถี่ยิ่งทำให้สายไม่ว่างหนักขึ้นอีก) TCP เลยพยายามประมาณ "เวลาปกติที่ควรรอ" จากประวัติ RTT ที่ผ่านมา บวกด้วย "ความผันผวน" (deviation) เผื่อไว้ด้วย

08 TCP Congestion Control — AIMD & Slow Start

TCP คุม sending rate ผ่านตัวแปร cwnd (congestion window) โดย:

Window = min( Advertised Window , Congestion Window )

พูดง่ายๆ คือ ส่งด้วยความเร็วเท่ากับ "องค์ประกอบที่ช้าที่สุด" ระหว่าง network กับ receiver

ADDITIVE INCREASE

เมื่อได้รับ ACK

cwnd += 1

ค่อยๆ เพิ่มทีละนิดเพื่อสำรวจว่า bandwidth ยังเหลือให้ใช้ไหม

MULTIPLICATIVE DECREASE

เมื่อเกิด packet loss (timeout)

cwnd *= 0.5

ลดฮวบทันทีครึ่งหนึ่ง เพื่อคลาย congestion ให้เร็วที่สุด

◆ ELI5

ทำไมเพิ่มทีละ 1 แต่ลดทีเดียวครึ่งหนึ่ง (ไม่ลดทีละ 1)? เพราะการ "เพิ่มช้าๆ" ปลอดภัย — ค่อยๆ ทดสอบว่าเครือข่ายรับไหวแค่ไหน แต่พอเจอสัญญาณว่า "แออัดแล้ว" (packet หาย) ต้อง "ถอยแรงๆ ทันที" เพื่อไม่ให้ปัญหาลุกลาม เหมือนขับรถ: ค่อยๆ เร่งความเร็วทีละนิด แต่พอเห็นเบรกไฟหน้าคันข้างหน้าต้องเบรกแรงทันที ไม่ใช่ค่อยๆ ผ่อน

TCP Sawtooth (ผลลัพธ์ของ AIMD) — ลองควบคุมเอง

◆ ลองเล่น — cwnd Simulator

Slow Start

ออกแบบมาให้ TCP "หา fair-share rate ได้เร็ว" ตอนเริ่ม connection ใหม่ (ไม่งั้นถ้าใช้ additive increase ทีละ 1 ตั้งแต่แรก จะใช้เวลานานมากกว่าจะไต่ถึง rate ที่เหมาะสม)

  1. เพิ่ม cwnd แบบเอ็กซ์โพเนนเชียล ทุกครั้งที่ได้ ACK (เท่ากับ cwnd เพิ่มเป็น 2 เท่าทุกๆ RTT) จนถึง SSThreshold
  2. ถ้า cwnd < SSThreshold → ยังอยู่ใน Slow Start, ถ้าไม่ → เข้าสู่ Congestion Avoidance (เพิ่มแบบ linear แทน)
  3. SSThreshold เริ่มต้นตั้งไว้สูงมาก พอมี packet loss ครั้งแรก → SSThreshold = cwnd / 2
◆ ELI5

Slow Start ชื่อฟังดูช้า แต่จริงๆ คือ "เร่งเร็วแบบทวีคูณ" (1→2→4→8...) เหมือนเปิดก๊อกน้ำแบบค่อยๆ หมุนเพิ่มทีละเท่าตัว จนกว่าจะรู้สึกว่าใกล้ล้นแล้ว (ถึง threshold) ถึงจะเปลี่ยนมาหมุนทีละนิดแบบระมัดระวัง (congestion avoidance) — ต่างจากการเปิดก๊อกทีละหยดตั้งแต่แรกซึ่งจะช้าเกินไป

09 Congestion Avoidance — DECbit & RED

Congestion Control (AIMD) คือการ "แก้ปัญหาหลังเกิดแล้ว" (reactive) — ส่วน Congestion Avoidance คือความพยายาม "ทำนายและป้องกันก่อนเกิด" โดยจับสัญญาณเตือนล่วงหน้า เช่น จุด "knee" ของกราฟ delay-vs-load

ROUTER-BASED

DECbit

  • ทุก packet มีบิต "Congestion Notification" (DECbit) อยู่ใน header
  • router ที่แออัดจะ set บิตนี้ (เกณฑ์: average queue length ≥ 1 packet ต่อ averaging period)
  • ผู้รับ copy บิตนี้ใส่ ACK ส่งกลับให้ผู้ส่ง
  • ผู้ส่งนับสัดส่วน DECbit ที่ถูก set ใน window: <50% → เพิ่ม rate แบบ additive, ≥50% → ลด rate แบบ multiplicative
ROUTER-BASED

RED (Random Early Detection)

  • ต่อยอดจาก DECbit แต่แจ้งเตือนแบบ "ไม่บอกตรงๆ" — ใช้การ drop packet แทน
  • โอกาส drop packet เพิ่มขึ้นตาม average queue length (ไม่ใช่ instantaneous) — ใช้ moving average (แบบ geometric) เพื่อทนต่อ burst ระยะสั้นได้
  • ยิ่ง flow ไหนส่งเยอะ ยิ่งมีโอกาสโดน drop มากตามสัดส่วน (คร่าวๆ)
  • การ drop จะถูก "กระจายตามช่วงเวลา" (spaced out) ผ่านตัวแปร count เพื่อไม่ให้ TCP ทุก flow เข้า slow-start พร้อมกันหมด

RED Drop Probability

ถ้า minTh < AvgLen < maxTh:
p̂ = maxP × (AvgLen − minTh) / (maxTh − minTh)
Pr(Drop) = p̂ / (1 − count×p̂)

ถ้า AvgLen ต่ำกว่า minTh → ไม่ drop เลย, ถ้าสูงกว่า maxTh → drop ทั้งหมด (probability = 1) ระหว่างสอง threshold นี้ → drop probability ไต่จาก 0 ถึง maxP แบบเชิงเส้น

◆ ELI5

DECbit เหมือนพนักงานร้านบอกลูกค้าตรงๆ ว่า "คิวเริ่มยาวแล้วนะ ช่วยชะลอหน่อย" ส่วน RED เหมือนพนักงานไม่บอกตรงๆ แต่ค่อยๆ "ปฏิเสธลูกค้าแบบสุ่ม" มากขึ้นเรื่อยๆ เมื่อคิวยาวขึ้น — ใครมาบ่อย/เยอะก็มีโอกาสโดนปฏิเสธมากกว่า วิธีนี้ทำให้แต่ละคน (แต่ละ TCP flow) ไม่ได้รับสัญญาณ "ให้ถอยพร้อมกันทีเดียว" ทั้งร้าน ซึ่งช่วยลดปัญหาข้อถัดไป (synchronization)

Synchronization ของ TCP sources

ถ้า router แจ้งเตือน congestion "พร้อมกันทุก flow" (เช่น drop-tail แบบ FIFO เต็มคิว) ทุก flow จะทำ AIMD sawtooth synchronized กัน — ขึ้นพร้อมกัน ลงพร้อมกัน ทำให้ aggregate traffic ที่ router เห็นก็กระเพื่อมขึ้นลงหนักตามไปด้วย (แย่ต่อ utilization โดยรวม)

การ drop แบบสุ่มของ RED ช่วย desynchronize — แต่ละ flow โดน drop คนละจังหวะ ทำให้ sawtooth ของแต่ละ flow เหลื่อมกันแทนที่จะซ้อนกัน ผลคือ aggregate flow โดยรวมราบเรียบขึ้นมาก (average คงที่กว่า)
