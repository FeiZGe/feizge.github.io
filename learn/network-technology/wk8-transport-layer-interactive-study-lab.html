OSI Layer 4 • Transport Layer

บทบาทของ Transport Layer ในสถาปัตยกรรมเครือข่าย

Transport Layer ทำหน้าที่ส่งข้อมูลแบบ End-to-End (Process-to-Process) ระหว่างแอปพลิเคชันบนโฮสต์ต้นทางและปลายทาง โดยใช้ Port Number เพื่อแยกแยะและส่งต่อแพ็กเก็ตไปยังโปรแกรมที่ถูกต้อง (Demultiplexing)

ELI5: อธิบายแบบเข้าใจง่ายใน 1 นาที (เปรียบเทียบ Network Layer vs Transport Layer)

📦 Network Layer (IP): เหมือนบุรุษไปรษณีย์ที่รู้วิธีส่งพัสดุจาก "ตึก A" ไปยัง "ตึก B" ตามเลขที่อยู่หน้าซอง (IP Address) แต่บุรุษไปรษณีย์ไม่รู้ว่าในตึกมีใครทำงานอยู่บ้าง

📬 Transport Layer (TCP/UDP): เหมือนแผนกสารบรรณ/ประชาสัมพันธ์ในตึก ที่คอยเปิดดูว่าต้องส่งต่อเอกสารนี้ให้ "พนักงานคนไหน" (ระบุด้วยหมายเลข Port เช่น เว็บเบราว์เซอร์, อีเมล, เกม) และถ้าใช้ TCP ก็จะคอยตรวจเช็กว่ากระดาษมาครบทุกแผ่น ถ้าตกหล่นจะโทรขอให้ส่งซ้ำใหม่ให้ทันที!

ฝั่ง Client (Active Close Lifecycle)

SYN_SENT: ส่ง SYN แล้ว กำลังรอ SYN+ACK

ESTABLISHED: ได้รับ SYN+ACK ส่ง ACK เรียบร้อย เริ่มรับส่งข้อมูล

FIN_WAIT_1: ส่ง FIN ขอปิด และรอ ACK

FIN_WAIT_2: ได้รับ ACK ของ FIN ตัวเองแล้ว รอรับ FIN จาก Server

TIME_WAIT: ได้รับ FIN และส่ง ACK แล้ว รอ 2 MSL (30-120 วินาที) ก่อนปิดสนิท

ฝั่ง Server (Passive Close Lifecycle)

LISTEN: เปิด Socket รอรับการติดต่อ

SYN_RCVD: ได้รับ SYN ส่ง SYN+ACK กลับไปแล้ว รอรับ ACK

ESTABLISHED: ได้รับ ACK แล้ว การเชื่อมต่อสมบูรณ์

CLOSE_WAIT: ได้รับ FIN จาก Client ส่ง ACK ยืนยัน และเตรียมเคลียร์ข้อมูล

LAST_ACK: ส่ง FIN ของตนเองออกไป และรอรับ ACK สุดท้ายก่อนปิด

กรณีที่ 1: RTT > Window Size

ผู้ส่งส่งข้อมูลจนเต็ม Window Size แล้ว แต่ยังต้องหยุดรอ ACK จากฝั่งรับ ทำให้เกิด Idle Time (เวลาว่าง) บนท่อส่ง แบนด์วิดท์ไม่ได้ถูกใช้งานเต็ม 100% (Under-utilized)

กรณีที่ 2: RTT = Window Size

เมื่อส่งข้อมูลเซกเมนต์สุดท้ายของ Window เสร็จพอดี ACK ของเซกเมนต์แรกก็วิ่งกลับมาถึง ทำให้ผู้ส่งสามารถส่งข้อมูลต่อไปได้ต่อเนื่องไม่สะดุด เกิด Full Utilization

💡 ในอัลกอริทึมเดิม การคูณ 2 แบบคงที่จะล้มเหลวเมื่อเครือข่ายคับคั่งเพราะ Variance ของ Delay พุ่งขึ้นแบบก้าวกระโดด อัลกอริทึมของ Jacobson จึงเพิ่มเทอม $+ 4 \times \text{Deviation}$ เพื่อป้องกัน False Timeout

ปัญหา Retransmission Ambiguity และ Karn's Algorithm

เมื่อเกิดการส่งซ้ำ (Retransmission) แล้วได้รับ ACK ตอบกลับมา ผู้ส่งจะ "ไม่รู้เลยว่า ACK นั้นเป็นของแพ็กเก็ตแรกที่แค่มาช้า หรือเป็นของแพ็กเก็ตตัวที่เพิ่งส่งซ้ำไป"

กฎข้อที่ 1 ของ Karn:

ห้ามนำค่า SampleRTT ของแพ็กเก็ตที่มีการส่งซ้ำมาอัปเดต $\text{EstimatedRTT}$ เด็ดขาด เพื่อป้องกันไม่ให้ค่า RTO เพี้ยน

กฎข้อที่ 2 (Exponential Backoff):

เมื่อเกิด Timeout ให้ปรับค่า RTO เพิ่มขึ้นเป็น 2 เท่าทันที ($\text{RTO} = 2 \times \text{RTO}$) สำหรับการส่งซ้ำรอบถัดไป

ห้องทดลอง TCP Congestion Control (Sawtooth Simulator)

ทดลองกลไก AIMD, Slow Start, Fast Retransmit และ Fast Recovery แบบ Real-time

Congestion Window (cwnd) 1 MSS
Slow Start Threshold (ssthresh) 16 MSS
Current Phase SLOW START (Exp)
Network Power Metric 0.95

1. Slow Start

เมื่อเริ่มต้นหรือหลัง Timeout ขนาด $cwnd$ จะเพิ่มขึ้น 2 เท่าทุกๆ 1 RTT (Exponential Growth) เพื่อค้นหาขีดความสามารถของช่องสัญญาณอย่างรวดเร็ว จนกระทั่งถึงจุด $ssthresh$

2. Congestion Avoidance (AIMD)

เมื่อ $cwnd \ge ssthresh$ จะเปลี่ยนเป็นการไต่ระดับขึ้นแบบเส้นตรง เพิ่มทีละ 1 MSS ต่อ 1 RTT เพื่อค่อยๆ ตรวจสอบว่าเครือข่ายเริ่มแน่นหรือยัง

3. Fast Retransmit / Recovery

เมื่อได้รับ 3 Duplicate ACKs จะส่งแพ็กเก็ตที่หายทันที และลด $cwnd$ ลงครึ่งหนึ่ง ($\text{ssthresh} = cwnd / 2, cwnd = \text{ssthresh}$) โดยไม่ต้องเริ่มจาก 1

Drop-Tail (Synchronized)

เปรียบเทียบผลรวมทราฟฟิก (Aggregate Flow) ระหว่าง Drop-Tail กับ RED:

⚠️ ปัญหาของ Drop-Tail: เมื่อคิวเต็ม ทุก Connection จะสูญเสียแพ็กเก็ตพร้อมกัน ทำให้ทุกโฮสต์ลดความเร็วลงพร้อมกัน เกิดทราฟฟิกรวมที่สวิงขึ้นลงรุนแรง

DECbit (Explicit Notification)

  • เราเตอร์ตรวจจับคิวเฉลี่ย $\ge 1$ แพ็กเก็ต จะเปิดบิต DECbit = 1 ในส่วนหัว
  • ผู้รับจะคัดลอก DECbit ใส่กลับมาในแพ็กเก็ต ACK
  • หากได้รับ DECbit $\ge 50\%$ ใน 1 Window $\to$ ผู้ส่งจะลดความเร็วลงแบบ Multiplicative
  • ข้อดี: ไม่ต้องสูญเสียแพ็กเก็ตจริงในการส่งสัญญาณเตือน

RED (Implicit Notification)

  • เราเตอร์สุ่มดรอปแพ็กเก็ตทิ้งล่วงหน้าก่อนที่บัฟเฟอร์จะล้นจริง
  • ดรอปตามสัดส่วนอัตราส่ง (Flow ที่ส่งเยอะมีโอกาสโดนดรอปมากกว่า)
  • กระจายการดรอปตามแกนเวลาเพื่อไม่ให้เกิดการเริ่ม Slow Start พร้อมกัน
  • ข้อดี: ใช้ได้กับเครื่องลูกข่าย TCP มาตรฐานเดิมทันที ไม่ต้องแก้ Protocol

Demultiplexing

การใช้หมายเลข Port เพื่อแจกจ่ายแพ็กเก็ตที่เข้ามาไปยังโพรเซสของแอปพลิเคชันที่ถูกต้องบนเครื่อง

TIME_WAIT State

สถานะของฝั่งเริ่มปิดการเชื่อมต่อที่ต้องรอเวลา 2 MSL (ราว 30-120s) เพื่อให้แน่ใจว่า ACK สุดท้ายไปถึง และเคลียร์แพ็กเก็ตเก่าที่ค้างในเครือข่าย

Karn's Algorithm

กฎที่ระบุว่า "ห้ามนำ SampleRTT ของแพ็กเก็ตที่มีการส่งซ้ำมาคำนวณ RTO" และให้ทำ Exponential Backoff คูณ 2 ค่า RTO ทุกครั้งที่ Timeout

AIMD (Additive Increase / Multiplicative Decrease)

กลไกควบคุมอัตราส่ง: เมื่อได้รับ ACK ให้เพิ่ม cwnd ทีละ 1 แต่เมื่อเกิด Timeout ให้ลด cwnd ลงครึ่งหนึ่งทันที เกิดเป็นรูปคลื่น Sawtooth

Global Synchronization

สภาวะที่ทุก TCP connection เกิด Timeout และลด/เพิ่มความเร็วพร้อมกัน ทำให้ทราฟฟิกรวมแกว่งขึ้นลงรุนแรง แก้ไขได้โดยใช้อัลกอริทึม RED

สูตรคำนวณสำคัญ:
• $\text{Effective Window} = \min(\text{Advertised Window}, cwnd)$
• $\text{Power} = \frac{\text{Load (Throughput)}}{\text{Delay}}$
• $\text{RTO} = \text{EstimatedRTT} + 4 \times \text{Deviation}$
