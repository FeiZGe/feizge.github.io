8.1

หน้าที่ของ Transport Layer & เปรียบเทียบ UDP vs TCP

อธิบายแบบ Feynman (เข้าใจใน 30 วิ)

ถ้า Network Layer (IP Address) คือบุรุษไปรษณีย์ที่ส่งจดหมายมาถึง "บ้านเลขที่" ของเรา (Host-to-Host)...
Transport Layer (Port Number) ก็คือคุณแม่บ้านที่รับจดหมายหน้าบ้านแล้วเดินเอาไปส่งให้ถูก "คนในบ้าน" (Process-to-Process) เช่น จดหมายเกมส่งให้พี่ชาย (Port 27015), จดหมายเว็บส่งให้น้องสาว (Port 80/443) โดยห่อข้อมูลเรียกว่า Segment

สถานการณ์จริง: โทรคุยสด vs โอนเงินธนาคาร

UDP (User Datagram Protocol): เหมือนตะโกนคุยกันตอนเล่นเกม ROV หรือคุยโทรศัพท์ (VoIP) ถ้าคำพูดขาดไปเสี้ยววินาที เราไม่ต้องการให้เขาย้อนกลับมาพูดคำเมื่อกี้ซ้ำ เพราะต้องการความไวสดใหม่ (Connectionless, Header เล็กแค่ 8 Bytes)
TCP (Transmission Control Protocol): เหมือนส่งสลิปโอนเงินหรือโหลดไฟล์ ZIP ห้ามตกหล่นแม้แต่ไบต์เดียว ต้องโทรนัดก่อนส่ง และมีใบเซ็นรับของทุกครั้ง (Connection-oriented, Header 20 Bytes)

คุณลักษณะ UDP (User Datagram Protocol) TCP (Transmission Control Protocol)
การสร้างการเชื่อมต่อ Connectionless (ส่งทันที ไม่ต้อง Handshake) Connection-oriented (ต้องทำ 3-Way Handshake ก่อน)
ขนาด Header 8 Bytes (Source Port, Dest Port, Length, Checksum) 20 Bytes (พื้นฐาน ไม่รวม Options)
ความน่าเชื่อถือ (Reliability) Unreliable (Best-effort) หายแล้วหายเลย เรียงสลับกันได้ Reliable Byte Stream (มี Seq#, Cumulative ACK, Retransmission)
Flow & Congestion Control ไม่มี (อัดข้อมูลตามที่ App สั่ง) มีครบ (Sliding Window `rwnd` และ Congestion Window `cwnd`)
ตัวอย่างโปรโตคอลที่ใช้ DNS (Port 53), DHCP, SNMP, CoAP, VoIP, Video Streaming ยุคแรก HTTP (80), HTTPS (443), SMTP (25), FTP, SSH, MQTT
8.2

TCP 3-Way Handshake, Sequence Number & Flow Control

อธิบายแบบ Feynman: เลข Sequence กับ ACK คืออะไร?

TCP ไม่ได้นับแพ็กเก็ตเป็น "กล่องที่ 1, 2, 3" แต่นับเป็น "เลขลำดับของตัวอักษร (Byte-stream)" เหมือนอ่านหนังสือทีละหน้า!
• Sequence Number (Seq): คือ "เลขไบต์แรก" ของข้อมูลในแพ็กเก็ตนั้น
• ACK Number (Cumulative ACK): คือคำพูดของคนรับที่บอกว่า "ฉันได้รับครบหมดแล้วนะ ตอนนี้ฉันกำลังรอไบต์หมายเลข X อยู่ ส่งเลข X มาได้เลย!"

สถานการณ์คำนวณในห้องสอบ

สมมติโฮสต์ A ส่ง Segment ที่มี Seq = 1000 และมีข้อมูลขนาด 500 Bytes (คือไบต์ที่ 1000 ถึง 1499)
เมื่อโฮสต์ B ได้รับครบถ้วน โฮสต์ B จะตอบกลับด้วย ACK = 1000 + 500 = 1500 (แปลว่า: ได้รับถึง 1499 แล้ว ส่งไบต์ที่ 1500 มาได้เลย!)
*ข้อควรระวัง:* ตอนทำ 3-Way Handshake แพ็กเก็ต SYN และ FIN แม้ไม่มีข้อมูล แต่จะกินเลข Sequence ไป 1 ลำดับเสมอ (เช่น ส่ง SYN Seq=x จะได้กลับมาเป็น ACK=x+1)

แยกให้ออก! ข้อสอบชอบถามความต่างระหว่าง Flow Control vs Congestion Control

1. Flow Control (กลัว "ผู้รับ" จุกตาย)

ป้องกันไม่ให้ผู้ส่ง ส่งข้อมูลเร็วเกินกว่าที่ Buffer ของเครื่องผู้รับปลายทาง จะรับไหว โดยผู้รับจะแจ้งขนาดพื้นที่ว่างกลับมาในช่อง Advertised Window (rwnd) ใน TCP Header

2. Congestion Control (กลัว "ถนน/Router" รถติด)

ป้องกันไม่ให้ผู้ส่ง ส่งข้อมูลมากเกินกว่าที่ Router ระหว่างทาง จะรับไหว โดยผู้ส่งจะประเมินความคับคั่งเองผ่านตัวแปร Congestion Window (cwnd)

สูตรจำกัดการส่งจริงของผู้ส่ง: LastByteSent - LastByteAcked ≤ min(rwnd, cwnd)

8.3

การคำนวณ Timeout (RTO) & กลไก TCP Congestion Control

สูตรคำนวณ Retransmission Timeout (RTO) ด้วย Exponential Weighted Moving Average (EWMA)

1. EstimatedRTT = (1 - α) × EstimatedRTT + α × SampleRTT (ปกติ α = 0.125)
2. DevRTT = (1 - β) × DevRTT + β × |SampleRTT - EstimatedRTT| (ปกติ β = 0.25)
3. TimeoutInterval (RTO) = EstimatedRTT + 4 × DevRTT

ทำไมต้องมี 4 × DevRTT? เพราะถ้าถนนแกว่งมาก (Jitter สูง) ค่า DevRTT จะกว้างขึ้น ทำให้เราเผื่อเวลา Timeout กว้างขึ้น ไม่รีบส่งซ้ำมั่วซั่ว (Premature Timeout)

Feynman: ทำไมต้องใช้ค่าเฉลี่ยถ่วงน้ำหนัก?

เหมือนคุณกะเวลาขับรถไปมหาลัย ปกติใช้เวลา 30 นาที (`EstimatedRTT`) แต่วันนี้ฝนตกหนักใช้เวลา 60 นาที (`SampleRTT`) พรุ่งนี้คุณคงไม่กะเวลาเป็น 60 นาทีเต็มๆ แต่จะขยับเวลาคาดการณ์ขึ้นนิดหน่อย (เอาน้ำหนักวันนี้มาคิดแค่ 12.5%)

1. Slow Start (โตแบบทวีคูณ)

เริ่มต้นที่ cwnd = 1 MSS ทุกครั้งที่ได้ ACK 1 ตัว จะบวกเพิ่ม 1 MSS ส่งผลให้ cwnd เพิ่มเป็น 2 เท่าทุกๆ 1 RTT (1 → 2 → 4 → 8...) จนกว่าจะชนเพดาน ssthresh

2. Congestion Avoidance (AIMD)

เมื่อ cwnd ≥ ssthresh จะเปลี่ยนมาค่อยๆ ขยับขึ้นแบบเส้นตรง (Additive Increase) คือ cwnd เพิ่มขึ้นแค่ +1 MSS ต่อ 1 RTT เพื่อหยั่งเชิงความจุของเน็ตเวิร์ก

3. เมื่อเกิด Packet Loss (Tahoe vs Reno)

ปรับเพดานใหม่ ssthresh = cwnd / 2 ทันที!
• ถ้าเกิด Timeout (หนัก): ทั้ง Tahoe และ Reno รีเซ็ต cwnd = 1 MSS
• ถ้าเกิด 3 Duplicate ACKs (เบา): Tahoe ลงไปเริ่มที่ 1 MSS แต่ Reno ทำ Fast Recovery ลดลงมาแค่ครึ่งเดียว (cwnd = ssthresh)

🎯 เก็งแนวข้อสอบเนื้อหาปกติ Week 8 (เรื่องใกล้เคียงที่อาจารย์สลับมาถามแทนได้!)
1. จากข้อ 1 (กราฟ Sampled RTT & RTO) → อาจถามเรื่อง Karn's Algorithm!

• ถ้าแพ็กเก็ตเกิด Timeout แล้วส่งซ้ำ (Retransmission) พอ ACK กลับมา ห้ามเอา SampleRTT รอบนั้นมาคำนวณ EstimatedRTT เด็ดขาด! เพราะไม่รู้ว่าเป็น ACK ของแพ็กเก็ตตัวแรกหรือตัวที่ส่งซ้ำ (เรียกว่า Retransmission Ambiguity) และให้ เพิ่มค่า RTO เป็น 2 เท่า (Exponential Backoff)

2. จากข้อ 2 (กราฟ RED) → อาจสลับไปถามกลไก DECbit หรือ Tail Drop!

• Tail Drop: รอจนคิวเต็ม 100% ค่อยตัดทิ้ง ทำให้เกิด Global Synchronization (ทุกเครื่องลด cwnd พร้อมกันแล้วเร่งพร้อมกัน เดี๋ยวก็เยอะ เดี๋ยวก็ว่าง จัดการยาก)
• DECbit: เราเตอร์คำนวณความยาวคิวเฉลี่ยตั้งแต่วงจรยุ่งรอบก่อน ถ้า ≥ 1 packet จะติ๊กบิตแจ้งเตือนใน Header และเมื่อผู้ส่งพบว่าแพ็กเก็ตใน Window ถูกติ๊กบิต ≥ 50% จะลด cwnd ลงครึ่งหนึ่งทันที (ถ้าน้อยกว่า 50% จะเพิ่มทีละ 1)

3. จากข้อ 3 (Advertised Window & Slow Start) → อาจถาม Fast Retransmit / Fast Recovery!

• Congestion Window (cwnd): ขีดจำกัดฝั่งผู้ส่งที่ปรับตามความคับคั่งของเครือข่าย (ต่างจาก Advertised Window rwnd ที่ปรับตาม Buffer ฝั่งผู้รับ)
• Fast Retransmit: เมื่อได้รับ 3 Duplicate ACKs ให้ส่งแพ็กเก็ตที่หายซ้ำทันทีโดยไม่ต้องรอ RTO หมดเวลา
• Fast Recovery (TCP Reno): ลด ssthresh = cwnd / 2 และตั้ง cwnd = ssthresh (ไม่ต้องกลับไปเริ่ม 1 MSS ใหม่เหมือน Timeout)

4. กราฟ Power vs Load & กราฟสะสมไบต์ X(t) (สไลด์ Wk8 ที่มีลายมืออาจารย์เน้น)

• นิยาม: Power = Load / Delay (จุดที่คุ้มค่าที่สุดคือ Optimal Load ก่อนคิวเริ่มสะสมพุ่งชัน)
• หากทราฟฟิกมีความแปรปรวนสูง (Burstiness) เส้นเพดานความจุ (Asymptote) ของกราฟ Delay จะเลื่อนมาทางซ้าย (เกิดรถติดเร็วขึ้นแม้ Load เฉลี่ยยังไม่เต็ม)
• กราฟ Cumulative Bytes: ระยะห่างแนวตั้งระหว่างเส้นข้อมูลขาเข้า A(t) กับขาออก D(t) คือ X(t) = ปริมาณข้อมูลที่ค้างอยู่ในคิวของ Router ณ เวลา t

9.1

Client-Server vs P2P & ระบบสมุดโทรศัพท์อินเทอร์เน็ต (DNS)

Feynman: DNS Iterative vs Recursive ต่างกันยังไง?

สมมติคุณตามหาห้องสมุดคณะ:
• Recursive Query (ฝากเพื่อนไปถามต่อให้จบ): คุณถามรุ่นพี่ (Local DNS) รุ่นพี่วิ่งไปถามยามหน้ามอ (Root) → ยามชี้ไปตึกวิศวะ (TLD) → ไปถามห้องธุรการ (Authoritative) จนได้คำตอบแล้วเดินกลับมาบอกคุณทีเดียว
• Iterative Query (ชี้เป้าให้ไปถามเอง): รุ่นพี่เดินไปถามยามหน้ามอ ยามตอบกลับมาว่า "ไม่รู้ห้องสมุดอยู่ไหน แต่ตึกวิศวะอยู่ตรงโน้น เดินไปถามเองนะ!" รุ่นพี่จึงต้องค่อยๆ ไล่ถามทีละตึกด้วยตัวเอง

ทริคจำชนิดของ DNS Resource Records (ออกสอบทุกปี!)
  • • Type A: ชื่อโดเมนจริง → IP Address (เช่น kmutnb.ac.th → 202.44.x.x)
  • • Type CNAME: ชื่อเล่น (Alias) → ชื่อจริง (Canonical Name)
  • • Type NS: ชื่อโดเมน → ชื่อเครื่อง Authoritative DNS Server ที่ดูแลโดเมนนั้น
  • • Type MX: ชื่อโดเมน → ชื่อเครื่อง Mail Server
9.2

HTTP (1.0 vs 1.1), Email (SMTP/POP3/IMAP), DASH Streaming & IoT (MQTT vs CoAP)

1. การคำนวณ RTT ของ HTTP & Cookies

• Non-Persistent HTTP (1.0): เปิด 1 TCP ส่งได้แค่ 1 Object ต้องเสียเวลา 2 RTT ต่อ 1 Object (1 RTT สำหรับ TCP Handshake + 1 RTT สำหรับขอและรับไฟล์)
• Persistent HTTP (1.1): เปิด TCP ครั้งเดียว (1 RTT แรก) แล้วส่งคำขอไฟล์ทั้งหมดต่อเนื่องกันได้เลย ประหยัดเวลา Handshake ซ้ำซ้อน
• Cookies: เนื่องจาก HTTP เป็น Stateless จึงต้องใช้ Cookie เก็บสถานะ Session ของผู้ใช้

2. ระบบ EMAIL (SMTP vs POP3/IMAP)

• SMTP (TCP Port 25): โปรโตคอลแบบ Push ใช้ส่งเมลจากเครื่องผู้ส่งไปหา Mail Server และ ใช้ส่งต่อข้อมูลระหว่าง Mail Server กับ Mail Server
• POP3 / IMAP: โปรโตคอลแบบ Pull ใช้สำหรับให้ผู้รับดึงเมลจาก Mail Server ของตัวเองมาเปิดอ่าน (ห้ามใช้ส่งระหว่างเซิร์ฟเวอร์!)

หัวข้อเปรียบเทียบ (IoT) MQTT (Message Queuing Telemetry Transport) CoAP (Constrained Application Protocol)
รูปแบบการสื่อสาร Publish / Subscribe ผ่านตัวกลางที่เรียกว่า Broker Request / Response (RESTful) คล้าย HTTP ย่อส่วน (มี GET, POST, PUT, DELETE)
Transport Layer ที่ใช้ รันอยู่บน TCP รันอยู่บน UDP (เบาและเร็วกว่าสำหรับเซ็นเซอร์จิ๋ว)
การรับประกันการส่ง (QoS) มี QoS 3 ระดับ: QoS 0 (At most once), QoS 1 (At least once), QoS 2 (Exactly once) ใช้ข้อความแบบ Confirmable (CON ต้องตอบ ACK) และ Non-confirmable (NON)
🎯 เก็งแนวข้อสอบเนื้อหาปกติ Week 9 (เรื่องใกล้เคียงที่อาจารย์สลับมาถามในข้อ 4 และ ข้อ 5 ได้!)
1. จากข้อ 4 (ถูก/ผิด เรื่อง MQTT, CoAP, POP3, EMAIL) → อาจสลับคำถามเป็น:
  • • "CoAP รันอยู่บน TCP" → ผิด! (CoAP รันบน UDP ส่วน MQTT รันบน TCP)
  • • "SMTP เป็นโปรโตคอลแบบ Pull ใช้ดึงเมลมาอ่าน" → ผิด! (SMTP เป็น Push ใช้ส่งเมล ส่วน POP3/IMAP เป็น Pull)
  • • "HTTP เป็น Stateful Protocol" → ผิด! (HTTP เป็น Stateless ต้องใช้ Cookie ช่วยจำสถานะ)
  • • "DNS ใช้โปรโตคอล UDP Port 53 เป็นหลัก" → ถูก! (เพื่อให้เร็วและไม่ต้องเสียเวลา 3-way handshake)
2. จากข้อ 5 (DASH & Manifest File) → อาจถามเรื่อง CDN หรือ HTTP 1.0 vs 1.1 แทน!
  • • ปัญหาของ Single Mega-Server: เป็น Single point of failure, ติดคอขวดที่ลิงก์ออก, และส่งข้อมูลซ้ำซ้อนไกลข้ามทวีป
  • • กลยุทธ์ CDN 2 แบบ: Enter Deep (ตั้งเซิร์ฟเวอร์ย่อยจำนวนมากลึกเข้าไปใน Access ISP ใกล้ผู้ใช้ที่สุด) vs Bring Home (ตั้งคลัสเตอร์ใหญ่ไม่กี่จุดที่ IXP ดูแลรักษาง่ายกว่า)
  • • คำนวณเวลา HTTP: หน้าเว็บมี HTML หลัก + รูป 10 รูป ถ้าเป็น Non-persistent HTTP/1.0 ต้องใช้ 2 RTT × (1 + 10) = 22 RTT แต่ถ้าเป็น Persistent HTTP/1.1 (Pipelined) ใช้แค่ 1 RTT (TCP) + 1 RTT (HTML) + 1 RTT (ขอ 10 รูปพร้อมกัน) = 3 RTT

10.1

ทำไม Wi-Fi ใช้ CSMA/CD ไม่ได้? & ปัญหา Hidden Terminal

Feynman: ปัญหา Hidden Terminal คืออะไร?

สมมติ นาย A กับ นาย C ยืนอยู่คนละฝั่งของตึกทึบ (มองไม่เห็นกันและไม่ได้ยินเสียงกัน) แต่ทั้งคู่อยากตะโกนคุยกับ อาจารย์ B (Access Point) ที่ยืนอยู่ตรงหัวมุมตึกพอดี
พอนาย A เริ่มพูด นาย C ไม่ได้ยินเสียงนาย A จึงคิดว่าไม่มีใครพูดอยู่ แล้วตะโกนแทรกขึ้นมาพร้อมกัน! ผลคือเสียงไปตีกันเละที่หูของอาจารย์ B (Collision ที่ฝั่งรับ)

วิธีแก้ของ 802.11: กลไก RTS / CTS และ SIFS vs DIFS

1. RTS/CTS: ก่อนส่งข้อมูลจริง A ส่งเฟรมสั้น RTS (Request to Send) ไปหา AP (B) → B ตอบกลับด้วย CTS (Clear to Send) กระจายไปทั่วรัศมี ทำให้ C ที่ซ่อนอยู่ได้ยิน CTS แล้วตั้งนาฬิกา NAV เงียบเสียงรอจนกว่า A จะส่งเสร็จ
2. ทำไมส่ง ACK ต้องรอแค่ SIFS (ไม่รอ DIFS)? เพราะ SIFS < DIFS เสมอ! การให้ผู้รับรอแค่ SIFS ก่อนส่ง ACK ทำให้ ACK ได้สิทธิ์ลัดคิวสูงสุด (Priority สูงสุด) โหนดอื่นที่ต้องรอให้คลื่นว่างครบ DIFS จึงแทรกคิวตัดหน้า ACK ไม่ได้!

1. ทำไม Wi-Fi (802.11) จึงใช้ CSMA/CD เหมือนสาย LAN (Ethernet) ไม่ได้?

• กำลังสัญญาณที่ส่งออกจากตัวเองแรงกลบสัญญาณอื่น จนการ์ด Wi-Fi ไม่สามารถฟังคลื่นไปพร้อมกับส่งข้อมูลได้ (ตรวจจับการชนขณะส่งไม่ได้)
• ปัญหา Hidden Terminal และ Fading ทำให้การที่ต้นทางไม่ได้ยินใครพูด ไม่ได้แปลว่าปลายทาง (AP) จะไม่เกิดการชนกัน จึงต้องใช้ CSMA/CA (Collision Avoidance) แทน

2. ทำไมเฟรม RTS/CTS จึงช่วยลดความเสียหายจากการชนได้ แม้ว่า RTS เองก็มีโอกาสชนกัน?

• เพราะเฟรม RTS และ CTS มีขนาดสั้นมาก เมื่อเทียบกับเฟรมข้อมูลจริง (DATA Frame) ที่อาจยาวหลายพันไบต์ หากเกิดการชนกันของเฟรม RTS จะเสียเวลาช่องสัญญาณไปเพียงนิดเดียว แต่ถ้าจองสำเร็จด้วย CTS แล้ว เฟรม DATA ขนาดใหญ่จะส่งผ่านได้โดยไม่ถูกโหนดอื่นชนเลย

3. การปรับความเร็วตามสภาพคลื่น (Dynamic Rate Adaptation)

• หากผู้ใช้เดินห่างออกจาก AP (ค่า SNR ลดลง / BER สูงขึ้น) สถานีจะลดระดับ Modulation ลง (เช่น จาก 256-QAM → 64-QAM → QPSK → BPSK) เพื่อรักษาความน่าเชื่อถือและให้ค่า BER ไม่เกินเกณฑ์ แม้จะได้ Data Rate ลดลงก็ตาม

4. โครงสร้าง MAC Address ในเฟรม 802.11 (Address 1, 2, 3)

• กรณีโฮสต์ A ส่งหา Router R ผ่าน AP: Address 1 (Receiver) = MAC ของ AP, Address 2 (Transmitter) = MAC ของโฮสต์ A, Address 3 = MAC ของ Router R (เพื่อให้ AP นำไปสร้างเฟรม Ethernet ส่งต่อให้ Router ได้ถูกต้อง)

11.1

เปรียบเทียบ 3G vs 4G LTE & การทำ Mobile IP Routing

Feynman: 3G กับ 4G ต่างกันตรงไหน? (ออกสอบข้อ 8!)

• 3G Network (แยก 2 ท่อ): มีทั้งท่อเก่าสำหรับคุยโทรศัพท์เสียง (Circuit-Switched ผ่าน MSC) และท่อใหม่สำหรับเล่นเน็ต (Packet-Switched ผ่าน SGSN/GGSN) วิ่งคู่ขนานกัน
• 4G LTE Network (รวมเป็น All-IP ท่อเดียว): ทุบท่อ Circuit-Switched ทิ้งทั้งหมด! ยุบรวมทั้งเสียง (VoLTE) และข้อมูลเน็ตให้กลายเป็น IP Packets วิ่งบน Packet-Switched Core (EPC) เพียงท่อเดียว และแยกส่วนสมองสั่งการ (Control Plane: MME/HSS) ออกจากท่อส่งข้อมูลจริง (Data Plane: S-GW/P-GW)

Feynman: Indirect Routing ทั้ง 6 ขั้นตอน (ออกสอบข้อ 9!)
  1. Mobile Node ย้ายออกจาก Home Network มาลงทะเบียนกับ Foreign Agent (FA)
  2. FA กำหนดที่อยู่ชั่วคราว Care-of-Address (COA) ให้กับ Mobile Node
  3. FA ติดต่อ Home Agent (HA) เพื่อแจ้งค่า COA ของ Mobile Node
  4. Correspondent Node ต้องการติดต่อ Mobile Node จึงส่งแพ็กเก็ตไปที่ Home Network
  5. HA ห่อหุ้ม (Encapsulate) แพ็กเก็ตที่ได้รับ แล้วส่งต่อ (Forward) ไปยัง COA ผ่าน FA
  6. FA แกะซอง (Decapsulate) แพ็กเก็ตออก แล้วส่งต่อให้ Mobile Node

  4. ขั้นที่ 4 (จุดต่าง!): Correspondent Agent ติดต่อสอบถามไปยัง Home Agent (HA) เพื่อขอทราบค่า COA ของ Mobile Node
  5. ขั้นที่ 5 (จุดต่าง!): Correspondent Agent ห่อหุ้ม (Encapsulate) แพ็กเก็ตแล้ว ส่งตรง (Forward) ไปยัง COA ที่ Foreign Agent (FA) โดยตรง (ไม่ต้องส่งผ่าน HA ซ้ำอีก)
  6. ขั้นที่ 6: Foreign Agent (FA) แกะซอง (Decapsulate) แพ็กเก็ตเพื่อส่งต่อให้ Mobile Node

ปูพื้นฐานให้เข้าใจง่ายที่สุด: RTT กับ RTO คืออะไร? และถ้า RTO < RTT หรือ RTO > RTT จะส่งผลอย่างไร? (อิงสไลด์ Wk8 หน้า 17–21)
1. นิยามตัวแปรพื้นฐานในกราฟ
  • • RTT (Round-Trip Time): เวลาเดินทางไป-กลับจริง นับตั้งแต่ผู้ส่งปล่อยแพ็กเก็ตออกไป จนกระทั่งได้รับ ACK ตอบกลับมา (ในกราฟข้อสอบ แกนนอนคือรอบการส่ง Transmission Round และแกนตั้งคือค่า Sampled RTT หน่วยเป็น ms ซึ่งเปลี่ยนตลอดเวลาตามความคับคั่งและการเปลี่ยนเส้นทาง Routing)
  • • RTO (Retransmission TimeOut): "เวลาตั้งปลุกรอสูงสุด" ที่ผู้ส่งตั้งไว้หลังจากส่งแพ็กเก็ต ถ้าเวลาเดินครบ RTO แล้วยังไม่ได้รับ ACK ผู้ส่งจะถือว่าแพ็กเก็ตสูญหายและส่งซ้ำทันที
  • • Guard Band (ระยะเผื่อปลอดภัย): ส่วนต่างที่บวกเผื่อเข้าไปเหนือค่า EstimatedRTT (คือ 4 × Deviation) เพื่อรองรับความแปรปรวนของคิว (Variance/Jitter)
2. เปรียบเทียบ 3 กรณี: RTO < RTT vs RTO > RTT (ออกสอบตรงๆ!)
  • ❌ กรณีที่ 1: ถ้า RTO < RTT (ตั้งเวลารอสั้นกว่าเวลาเดินทางจริง เช่น RTO = 3 ms แต่ RTT = 4–7 ms)
    → เกิด Premature Timeout (False Timeout) นาฬิกาปลุกดังก่อนที่ ACK จะเดินทางกลับมาถึง ทำให้ผู้ส่งส่งแพ็กเก็ตซ้ำโดยไม่จำเป็น (Unnecessary Retransmission) เปลืองแบนด์วิดท์และทำให้ได้ ACK ซ้ำ
  • ✅ กรณีที่ 2: ถ้า RTO > RTT เล็กน้อยอย่างเหมาะสม (มี Guard Band พอดี เช่น RTO = 8 ms เมื่อ RTT สูงสุด = 7 ms)
    → เหมาะสมที่สุดในสภาวะนั้น เพราะ ACK ทุกตัวกลับมาทันก่อนหมดเวลา ไม่เกิดการส่งซ้ำมั่วซั่ว
  • ⚠️ กรณีที่ 3: ถ้า RTO >> RTT (ตั้ง RTO สูงเกินไปมากๆ เช่น RTO = 50 ms ทั้งที่ RTT = 3–7 ms)
    → เมื่อเกิด Packet Loss จริง ผู้ส่งจะรอนานเกินไปกว่าจะรู้ตัวและส่งข้อมูลซ้ำ (Wait too long to retransmit) ทำให้เกิดความหน่วงสูงและ Throughput ตกลง
วิธีอ่านกราฟในโจทย์ข้อ 1: กราฟแสดงจุดค่า Sampled RTT (ms) ในแต่ละ Transmission Round (รอบที่ 1 ถึง 48) โดยจุดต่ำสุดอยู่ที่ 3 ms และจุดสูงสุดอยู่ที่ 7 ms (ค่าส่วนใหญ่วิ่งอยู่ระหว่าง 4 ms ถึง 7 ms)
1.1) หากกำหนดให้ค่า RTO เป็นค่าคงที่เท่ากับ 3 ms จะเกิดอะไรขึ้น?

✅ คำตอบส่งอาจารย์: จะเกิดปัญหา Premature Timeout (หมดเวลาเร็วเกินไป เพราะ RTO < RTT ในเกือบทุกรอบ) เนื่องจากค่า RTT จริงส่วนใหญ่ในกราฟมีค่าระหว่าง 4 – 7 ms ซึ่งสูงกว่า 3 ms ทำให้แม้แพ็กเก็ตจะไม่ได้สูญหาย แต่ ACK ยังเดินทางกลับมาไม่ทันครบ 3 ms ผู้ส่งก็จะเข้าใจผิดว่าแพ็กเก็ตหายและทำการ ส่งแพ็กเก็ตซ้ำโดยไม่จำเป็น (Unnecessary Retransmission) เกือบทุกรอบ ส่งผลให้มีแพ็กเก็ตซ้ำซ้อนทะลักเข้าสู่เครือข่ายและเกิดความคับคั่งมากขึ้น

1.2) หากกำหนดให้ RTO มีค่าเท่ากับ 8 ms จะเกิดอะไรขึ้น?

✅ คำตอบส่งอาจารย์: เนื่องจากค่า RTT สูงสุดในกราฟคือ 7 ms การตั้ง RTO = 8 ms (ซึ่ง RTO > RTT ทุกจุดในกราฟเล็กน้อย) จะช่วยให้ ไม่เกิดปัญหา Premature Timeout เลย (ไม่มีการส่งซ้ำโดยไม่จำเป็นในช่วงเวลานี้) อย่างไรก็ตาม การกำหนดเป็นค่าคงที่ที่ 8 ms มีข้อเสียคือ: ในช่วงที่ RTT จริงลดลงต่ำ (เช่น 3 ms) หากเกิด Packet Loss จะต้องรอนานถึง 8 ms กว่าจะส่งซ้ำ และหากอนาคตเครือข่ายคับคั่งขึ้นจน RTT เกิน 8 ms ค่าคงที่นี้ก็จะเกิด Premature Timeout อีก

1.3) จงอธิบายวิธีการกำหนดค่า RTO ที่ดี

✅ คำตอบส่งอาจารย์: ไม่ควรกำหนดเป็นค่าคงที่ แต่ต้องใช้ Adaptive RTO ที่แปรผันตามความคับคั่งของเครือข่าย โดยประเมินทั้งค่าเฉลี่ยถ่วงน้ำหนัก (EstimatedRTT) และค่าความแปรปรวนของความหน่วง (Deviation / DevRTT) เพื่อเผื่อ Guard Band ตามอัลกอริทึมของ TCP:
Difference = SampleRTT - EstimatedRTT
EstimatedRTT = EstimatedRTT + δ(Difference)
Deviation = Deviation + δ(|Difference| - Deviation)
RTO = μ × EstimatedRTT + φ × Deviation (μ≈1, φ≈4)

ทริคจำไปสอบถ้าอาจารย์เปลี่ยนตัวเลขในกราฟข้อ 1: ดูขอบบนสุดและขอบล่างสุดของจุดในกราฟ! ถ้าโจทย์ถามค่า RTO ที่ ต่ำกว่ายอดกราฟ (`RTO < RTT`) → ตอบ เกิด Premature Timeout ส่งแพ็กเก็ตซ้ำโดยไม่จำเป็น ทันที! แต่ถ้าโจทย์ถามค่า RTO ที่ สูงกว่ายอดกราฟ (`RTO > RTT`) → ตอบว่า ไม่เกิด Premature Timeout ในช่วงนั้น แต่หากตั้งสูงเกินไป เวลาแพ็กเก็ตสูญหายจริงจะรอนานกว่าจะส่งซ้ำ (Slow reaction to loss)

1. ความหมายของแกนกราฟและจุดสำคัญ
  • • แกนนอน (AvgLen - Average Queue Length): ความยาวคิวเฉลี่ยของแพ็กเก็ตที่สะสมอยู่ใน Router (ที่ต้องใช้ ค่าเฉลี่ย แทนคิวจริง เพื่อให้ยอมรับทราฟฟิกที่พุ่งมาเป็นก้อนสั้นๆ หรือ Tolerant of short-term bursts ได้โดยไม่ดรอปมั่ว)
  • • แกนตั้ง (P_drop - Drop Probability): ความน่าจะเป็นที่เราเตอร์จะสุ่มทิ้ง (Drop) แพ็กเก็ตที่เพิ่งวิ่งเข้ามาใหม่ มีค่าตั้งแต่ 0 (ไม่ดรอปเลย = 0%) ไปจนถึง 1 (ดรอปทิ้งทั้งหมด = 100%)
  • • MinThreshold (ในข้อสอบคือเลข 10): จุดเริ่มเฝ้าระวัง ถ้าคิวเฉลี่ย AvgLen ≤ 10 เราเตอร์จะไม่ดรอปแพ็กเก็ตเลย (P_drop = 0)
  • • MaxThreshold (ในข้อสอบคือเลข 15): ขีดจำกัดสูงสุดของคิว ถ้าคิวเฉลี่ยทะลุเกิน 15 ไปแล้ว เราเตอร์จะดรอปแพ็กเก็ตที่เข้ามาใหม่ 100% ทันที (P_drop = 1.0)
  • • Pmax (ในข้อสอบคือ 0.5 สำหรับ RED-1 และ 0.7 สำหรับ RED-2): ความน่าจะเป็นสูงสุดในการสุ่มดรอป ณ จุดที่คิวแตะระดับ MaxThreshold (15) พอดี
2. ทำไมต้องสุ่มดรอปล่วงหน้า & ระวังจุดหลอก P_Throughput!
  • • เหตุผลที่ใช้ RED: ถ้าใช้แบบเก่า (Tail Drop รอคิวเต็มค่อยทิ้ง) ทุกโฮสต์จะโดนดรอปพร้อมกันแล้วลด/เพิ่ม Window พร้อมกัน (เรียกว่า Global Synchronization ทำให้ทราฟฟิกรวมแกว่งหนัก เดี๋ยวก็เยอะ เดี๋ยวก็ว่าง) การสุ่มดรอปล่วงหน้าของ RED ช่วย Desynchronize TCP sources ให้กราฟทราฟฟิกรวมเรียบเนียน (Smooth) และใครส่งเยอะก็มีโอกาสโดนดรอปเยอะตามสัดส่วน
  • • ⚠️ จุดหลอกสำคัญในข้อสอบข้อ 2: กราฟบอกค่า โอกาสโดนดรอป (P_drop) แต่โจทย์ถามหา P_Throughput (เปอร์เซ็นต์แพ็กเก็ตที่รอดผ่านออกจาก Router) ดังนั้นต้องคำนวณจาก:
    P_Throughput (%) = (1 - P_drop) × 100%
✅ เฉลยคำตอบทั้ง 4 ข้อย่อย (2.1 – 2.4) พร้อมวิธีคิด:
2.1) Avg queue length = 10 packets และใช้ RED-2:
• ที่ AvgLen = 10 (อยู่ที่จุดเริ่มต้น MinThreshold = 10 พอดี) ค่าความน่าจะเป็นในการดรอป P_drop = 0 (ดรอป 0%)
• ดังนั้น P_Throughput = (1 - 0) × 100% = 100%
2.2) Avg queue length = 18 packets และใช้ RED-1:
• ที่ AvgLen = 18 ซึ่งสูงเกินค่า MaxThreshold = 15 ไปแล้ว เราเตอร์จะดรอปแพ็กเก็ตทั้งหมด (P_drop = 1.0 หรือดรอป 100%)
• ดังนั้น P_Throughput = (1 - 1.0) × 100% = 0%
2.3) Avg queue length = 13 packets และใช้ RED-1 (Pmax = 0.5):
• หา P_drop จากสมการเส้นตรงช่วง [10, 15]: P_drop = 0.5 × (13 - 10) / (15 - 10) = 0.5 × (3 / 5) = 0.30 (ดรอป 30%)
• ดังนั้น P_Throughput = (1 - 0.30) × 100% = 70%
2.4) Avg queue length = 13 packets และใช้ RED-2 (Pmax = 0.7):
• หา P_drop จากสมการเส้นตรงช่วง [10, 15]: P_drop = 0.7 × (13 - 10) / (15 - 10) = 0.7 × (3 / 5) = 0.42 (ดรอป 42%)
• ดังนั้น P_Throughput = (1 - 0.42) × 100% = 58%
📝 แนวคำตอบตรงช่อง "อธิบายแนวคิด" (เขียนตามนี้ได้คะแนนเต็ม):
กราฟ RED แสดงความน่าจะเป็นในการดรอปแพ็กเก็ต (P_drop) ตามความยาวคิวเฉลี่ย (AvgLen) โดยถ้า AvgLen ≤ 10 จะไม่ดรอปเลย (P_drop = 0), ถ้าอยู่ระหว่าง 10 < AvgLen ≤ 15 จะสุ่มดรอปเพิ่มขึ้นแบบเชิงเส้นตามสูตร P_drop = Pmax × (AvgLen - 10) / (15 - 10) และถ้า AvgLen > 15 จะดรอปทั้งหมด (P_drop = 1.0) จากนั้นหาเปอร์เซ็นต์แพ็กเก็ตที่ผ่านออกจากเราเตอร์ได้จาก P_Throughput = (1 - P_drop) × 100%

Advertised Window & Slow Start

3.1) Advertised Window (rwnd) คืออะไร?

✅ คำตอบ: คือขนาดพื้นที่ว่างใน Buffer ของฝั่งผู้รับ (Receiver Buffer) ที่ผู้รับแนบแจ้งกลับมาใน TCP Header เพื่อทำหน้าที่ Flow Control ป้องกันไม่ให้ผู้ส่งส่งข้อมูลเร็วเกินกว่าที่ผู้รับจะประมวลผลทัน

3.2) Slow Start ช่วยเพิ่มประสิทธิภาพของ TCP อย่างไร?

✅ คำตอบ: ช่วยให้ TCP เริ่มต้นส่งข้อมูลอย่างปลอดภัยที่ cwnd = 1 MSS แล้ว เพิ่มขนาด cwnd เป็น 2 เท่าทุกๆ 1 RTT (Exponential Growth) ทำให้สามารถไต่ระดับความเร็วไปหาแบนด์วิดท์ที่ว่างของเครือข่ายได้อย่างรวดเร็วโดยไม่ทำให้เครือข่ายล่มตั้งแต่เริ่มส่ง

  • 1. Manifest File คืออะไร: คือไฟล์ข้อมูลเมตา (รายการสารบัญ) ที่เซิร์ฟเวอร์ส่งให้เครื่องลูกข่าย (Client) ตอนเริ่มต้นสตรีมวิดีโอ โดยภายในระบุรายการที่อยู่ URL ของชิ้นส่วนวิดีโอ (Video Chunks) ทั้งหมดที่ถูกเข้ารหัสแยกไว้ใน ระดับความละเอียด/อัตราบิตเรต (Bitrate Versions) ที่แตกต่างกัน
  • 2. บทบาทต่อการทำ Multimedia Streaming: ช่วยให้ ฝั่งผู้รับ (Client) มีความฉลาดในการปรับเปลี่ยนคุณภาพวิดีโอ โดย Client จะคอยวัดความเร็วแบนด์วิดท์ระหว่างตัวเองกับเซิร์ฟเวอร์ แล้วใช้ข้อมูลใน Manifest File เลือกร้องขอ (HTTP GET) ชิ้นส่วนวิดีโอ (Chunk) ถัดไปที่มี Bitrate สูงสุดที่เครือข่ายขณะนั้นรองรับไหวโดยไม่กระตุก
เก็งข้อสอบเมื่ออาจารย์ "ถามเรื่องใกล้เคียงในหัวข้อเดียวกัน":
  • ถ้าถามเรื่อง CDN แบบ Enter Deep vs Bring Home:

✅ คำตอบสำหรับเขียนในห้องสอบ:

1. ปัญหา Hidden Terminal คือ: สภาวะที่สถานีไร้สาย 2 เครื่อง (เช่น A และ C) ต้องการส่งข้อมูลไปยังสถานีรับเดียวกัน (AP หรือ B) แต่ A และ C อยู่ห่างกันเกินระยะส่งสัญญาณหรือมีสิ่งกีดขวาง ทำให้ไม่ได้ยินสัญญาณของกันและกัน จึงส่งข้อมูลออกมาพร้อมกันและเกิดการชนกัน (Collision) ที่ปลายทาง B

2. วิธีแก้ไขของ 802.11 (กลไก RTS/CTS): ผู้ส่ง (A) ส่งเฟรมสั้น RTS (Request to Send) ไปยัง AP (B) และ AP ตอบกลับด้วยเฟรม CTS (Clear to Send) ซึ่งโหนด C ที่ซ่อนอยู่จะได้ยิน CTS จึงตั้งตัวนับเวลา NAV (Network Allocation Vector) เพื่อระงับการส่งข้อมูลของตนเองจนกว่า A จะส่งข้อมูลและรับ ACK เสร็จสิ้น

✅ คำตอบสำหรับเขียนในห้องสอบ:

เนื่องจาก SIFS มีระยะเวลาสั้นกว่า DIFS เสมอ การให้ผู้รับรอเพียงแค่ระยะเวลา SIFS ก่อนส่งเฟรม ACK จะทำให้ เฟรม ACK ได้รับสิทธิ์สูงสุด (Highest Priority) ในการเข้าใช้ช่องสัญญาณต่อทันที โดยที่สถานีอื่นๆ (ซึ่งต้องรอให้ช่องสัญญาณว่างครบเวลา DIFS ที่ยาวกว่า) ไม่สามารถแทรกคิวส่งข้อมูลใหม่ตัดหน้าเฟรม ACK ได้

2 MSC ตั้งค่าเส้นทางใหม่ (จัดสรรทรัพยากร) ไปยังเสา New BS
3 New BS จัดสรรช่องสัญญาณวิทยุ (Radio Channel) เตรียมไว้สำหรับรับ Mobile Node และแจ้งตอบรับ
4 New BS ส่งสัญญาณแจ้งกลับไปยัง MSC และ Old BS ว่าทางเดินใหม่พร้อมใช้งานแล้ว
5 Old BS สั่งให้ Mobile Node สลับช่องสัญญาณไปเกาะกับเสาใหม่ (New BS)
6 Mobile Node ส่งสัญญาณยืนยันผ่าน New BS ไปยัง MSC ว่าย้ายสำเร็จ จากนั้น MSC จึงคืนทรัพยากรของเสาเดิม (Old BS)
🎯 เก็งลำดับที่ 3 (ไม่ใช่ Mobility): ลำดับการส่งข้อมูลด้วย CSMA/CA + RTS/CTS (Wk10) สไลด์ Wk10

ถ้าอาจารย์เปลี่ยนข้อเรียงลำดับไปออกเรื่อง ขั้นตอนการจองคลื่นและส่งข้อมูลใน Wi-Fi (802.11 CSMA/CA with RTS/CTS):

ลำดับ เหตุการณ์ตามลำดับเวลาจริง (1 → 6) ของ 802.11 RTS/CTS
1 Sender (A) ตรวจสอบว่าช่องสัญญาณว่างครบระยะเวลา DIFS (หรือทำ Random Backoff จนครบ)
2 Sender (A) ส่งเฟรมสั้น RTS (Request to Send) ที่ระบุระยะเวลาจองคลื่นไปยัง Access Point (AP)
3 AP (Receiver) รอเป็นระยะเวลาสั้นๆ เท่ากับ SIFS แล้วกระจายเฟรม CTS (Clear to Send) ตอบกลับ
4 สถานีอื่นๆ (Hidden Nodes) ที่ได้ยิน CTS ตั้งตัวนับเวลา NAV (Network Allocation Vector) เพื่อระงับการส่งข้อมูลของตน
5 Sender (A) รอเป็นระยะเวลาเท่ากับ SIFS หลังจากได้รับ CTS แล้วเริ่มส่งเฟรมข้อมูลจริง (DATA Frame)
6 AP (Receiver) ได้รับข้อมูลถูกต้อง จึงรอเป็นระยะเวลาเท่ากับ SIFS แล้วส่งเฟรม ACK ตอบกลับให้ Sender
🎯 เก็งลำดับที่ 4 (ไม่ใช่ Mobility): ลำดับ DNS Iterative Query + การเปิดเว็บ HTTP (Wk9) สไลด์ Wk9

ถ้าอาจารย์ถามลำดับเหตุการณ์เมื่อผู้ใช้พิมพ์ URL ในเบราว์เซอร์เพื่อค้นหา IP ด้วย DNS แล้วดึงหน้าเว็บด้วย HTTP:

ลำดับ เหตุการณ์ตามลำดับเวลาจริง (1 → 6) ของ DNS & HTTP
1 Client (Host) ส่งคำถาม DNS Query ไปยัง Local DNS Server เพื่อขอทราบ IP Address ของชื่อโดเมนปลายทาง
2 Local DNS Server สอบถามไปยัง Root DNS Server และได้รับรายชื่อของ TLD DNS Server ตอบกลับมา
3 Local DNS Server สอบถามไปยัง TLD DNS Server (เช่น .com, .th) และได้รับชื่อของ Authoritative DNS Server ตอบกลับมา
4 Local DNS Server สอบถามไปยัง Authoritative DNS Server จนได้หมายเลข IP Address จริง แล้วส่งคำตอบกลับให้ Client
5 Client สร้างการเชื่อมต่อ TCP (3-Way Handshake: SYN → SYN+ACK → ACK) ไปยังหมายเลข IP ของ Web Server
6 Client ส่งคำขอ HTTP GET Request เข้าไปในท่อ TCP และ Web Server ตอบกลับด้วย HTTP Response พร้อมไฟล์ HTML

ปูพื้นฐานความหมายของแกนกราฟ ตัวแปรทุกตัว และลองเลื่อนสไลเดอร์เพื่อดูว่าเมื่ออาจารย์เปลี่ยนตัวเลขในห้องสอบ คำตอบจะเปลี่ยนไปอย่างไร

1. พื้นฐานกราฟ TCP Sawtooth

• แกนนอน: เวลาเป็นรอบ RTT
• แกนตั้ง (cwnd): จำนวนแพ็กเก็ต (MSS) ที่ส่งได้โดยไม่ต้องรอ ACK
• ssthresh: เส้นประเพดานเปลี่ยนเกียร์ ต่ำกว่าเส้นนี้เพิ่มเป็น 2 เท่า (Slow Start) สูงกว่าเส้นนี้เพิ่มทีละ +1 (Congestion Avoidance)

2. พื้นฐานกราฟ BER vs SNR (Eb/N0)

• แกนนอน (Eb/N0 หรือ SNR): ความแรงสัญญาณเทียบกับคลื่นรบกวน (ยิ่งขวา = สัญญาณยิ่งชัด)
• แกนตั้ง (BER): โอกาสบิตผิดพลาด (ยิ่งต่ำ = ยิ่งดี เช่น 10^-6 ผิดแค่ 1 ในล้านบิต)

3. พื้นฐานกราฟ RED Queue

• แกนนอน (AvgLen): ความยาวคิวเฉลี่ยใน Router
• แกนตั้ง (P_drop): โอกาสสุ่มทิ้งแพ็กเก็ต
• P_Throughput: เปอร์เซ็นต์ที่รอดออกไปได้ คำนวณจาก (1 - P_drop) × 100%

4. พื้นฐานแผนภาพเวลา 802.11

• DIFS: เวลารอคลื่นว่างก่อนเริ่มส่งข้อมูลใหม่ (ยาวกว่า)
• SIFS: เวลารอสั้นที่สุดก่อนตอบ CTS หรือ ACK เพื่อให้ได้สิทธิ์ลัดคิวสูงสุด
• NAV: เวลาที่โหนดอื่นตั้งนาฬิกางดส่งข้อมูล
